# Путь картинки: от загрузки до игрового объекта

Памятка — в каком порядке обрабатывать картинки и куда что класть, чтобы не путать `assets/sprites/` и `assets/refs/` и не терять уже готовые варианты (как случилось с `tank_water` — чуть не продублировали то, что уже было). Пишется для агента, который обрабатывает картинки через GitHub-подключение (без настоящей папки на диске), но правила те же и для обычной папки проекта.

## 0. Три корзины репозитория

```
tools/           ← конструкторы-редакторы (это код, не трогаем при обработке картинок)
assets/sprites/  ← ПРОМЕЖУТОЧНОЕ: сырые/необработанные загрузки, ждут разбора
assets/refs/     ← ГОТОВОЕ: правильно названные превью, их видит Object Plan
data/objects/    ← ГОТОВОЕ: игровые объекты ОС (JSON), ссылаются на assets/sprites/
```

`assets/sprites/` и `assets/refs/` — **разные вещи с разным назначением**, не стадии одного файла:

| | `assets/sprites/` | `assets/refs/` |
|---|---|---|
| Что лежит | Сырьё: как попало названные/не названные картинки, ждущие разбора. Также — уже разложенные по `<категория>/<подтип>/` финальные спрайты объектов (их туда кладёт сама ОС при сохранении, либо мы — вручную копируя из `refs`, см. §3) | Правильно названные `<id>_<вариация>_<idle\|broken\|icon>.png` — **только превью/референс**, их смотрит Object Plan, в игру они НЕ идут напрямую |
| Кто читает | ОС/Room Editor/Building Editor — по пути `appearance.asset` и т.п. из `data/objects/*.json` | Object Plan (`refStateThumbs()`), Asset Renamer (источник и назначение) |
| Что писать сюда | Новые необработанные загрузки (если не идут сразу через Image Prep Tool в `refs`) | Image Prep Tool (сразу, с именем) или Asset Renamer (после сортировки) |

## 1. Как картинка попадает в `assets/refs/` (готовое превью)

Два инструмента, выбор зависит от того, что на входе:

**Image Prep Tool** (`tools/ipt/image-prep-tool/`) — когда на одном листе несколько объектов или нужно обрезать/почистить. Лист → рамкой или авто по альфа-каналу → слой → имя из каталога Object Plan (панель слева, раздел/объект/вариация, выбор «липкий» — держится между вырезками) → «Сохранить всё» пишет каждый слой **сразу** в `assets/refs/<категория>/<id>_<вариация>[_idle].png`. Ничего в `assets/sprites/` не остаётся — исходный лист сама ОС/IPT не трогает (если лист грузили не из `assets/sprites/`, а просто выбрали файл с компьютера).

**Asset Renamer** (`tools/asset-renamer/`) — когда уже есть пачка отдельных, но как попало названных файлов (источник — обычно `assets/sprites/`, назначение — `assets/refs/`). Разбирает имя файла по разделу/объекту/вариации (подсказка, правится руками), ставит состояние (хороший/сломано/иконка), переносит под итоговым именем в `assets/refs/<категория>/` **и удаляет исходный файл из `assets/sprites/`**.

### Подпапки-категории внутри `assets/refs/`

`assets/refs/` разложен по категории ОС (`assets/refs/furniture/`, `assets/refs/item/`, `assets/refs/tool/` и т.д. — те же 13 категорий, что и в `assets/sprites/`), а не лежит плоским списком. Причина чисто техническая: страница GitHub обрезает список файлов в одной папке на 1000 — это только ограничение веб-интерфейса (ни git, ни Git Trees API, которым пользуются все редакторы, такого лимита не имеют), но чтобы список было видно в браузере, обе точки записи сами выбирают подпапку:

- **Image Prep Tool** знает категорию сразу — её даёт `item.c` из каталога Object Plan в момент выбора объекта в панели именования (хранится как `layer.category`, см. `08-naming-panel.js`/`09-save.js`). Если слой сохраняют без выбора в панели (редкий случай) — файл идёт в плоский корень `assets/refs/`.
- **Asset Renamer** категорию не знает напрямую (его раздел/объект/вариация — текст, а не ссылка на каталог), поэтому подключает словарь Object Plan (`02-vocab.js` + `03…05-data-*.js`, без `01-core-utils.js` — там конфликтующие имена) и подбирает категорию по `id = раздел_объект` (`categoryForPending()` в `05-actions.js`). Не нашёлся в каталоге (новый, ещё не заведённый тип) — тоже в плоский корень.
- Поиск превью в Object Plan (`refThumbFor`/`refStateThumbs`, `07-store.js`) сравнивает только **имя файла**, путь к нему не важен — так что подпапки ничего не ломают, их просто не обязательно поддерживать явно где-то ещё.
- Если переносите файлы руками (не через эти два инструмента) — кладите в `assets/refs/<категория>/`, категорию берите из `c` соответствующей записи в `object-plan/js/03…05-data-*.js`.

### Правило, которое легко забыть

**Прежде чем присваивать новой картинке id/вариацию — проверь, нет ли в `assets/refs/` уже файлов с этим id.** Папка теперь разложена по категориям (см. выше), искать нужно рекурсивно:
```bash
find assets/refs -iname "<id>_*"
```
Если есть — новая картинка почти наверняка **ещё одна вариация** того же объекта (просто не дублируй вариацию, которая уже занята), а не повод считать объект «без картинок». Разные картинки одного объекта — это нормально и ожидаемо (в плане у каждого id обычно 3-5 вариаций, `item.v`).

### Как обрабатывать то, что лежит в `assets/sprites/` «на обработку» (без доступа к самому Image Prep Tool — руками/скриптом)

1. `ls assets/sprites` — всё, что лежит **прямо в корне** (не в `<категория>/<подтип>/`) — сырьё на обработку. Вложенные папки `assets/sprites/<категория>/...` — это уже готовые финальные спрайты объектов (см. §3), их не трогаем.
2. Для каждого файла — посмотреть картинку, подобрать id по каталогу Object Plan (`tools/object-plan/js/03…05-data-*.js`, поле `v` — вариации) **и** свериться с правилом выше (уже есть ли такой id в `refs`).
3. Переименовать и перенести: `git mv assets/sprites/<файл> assets/refs/<категория>/<id>_<вариация-en>_idle.png` (категория — поле `c` найденной записи плана; состояние по умолчанию `idle`, если явно не повреждённый/иконка).
4. Исходник в `assets/sprites/` после переноса не остаётся — `git mv` это и делает.
5. Закоммитить с понятным сообщением, как это делает сам Asset Renamer («Process … into assets/refs/»).

## 2. `assets/refs/` ≠ в игре — объект нужно «подключить» отдельно

Картинка в `assets/refs/` даёт превью в Object Plan, но **не делает объект видимым** в Room Editor/Building Editor/ОС. Для этого в `data/objects/<id>.json` должно быть:

- `appearance.asset` — путь вида `<категория>/<подтип>/<id>_<translit(название)>.png`
- реальный файл по этому пути внутри `assets/sprites/` (не `assets/refs/`!)

Если объект уже создан (JSON существует), а картинка только что появилась в `assets/refs/` — доносим её до игры так:
```bash
git mv assets/refs/<файл> assets/sprites/<appearance.asset-путь-из-JSON>
# или cp, если нужно оставить файл в refs для Object Plan тоже
```
и при необходимости поправить `appearance.imageWidth/imageHeight` в JSON по реальным размерам PNG (IHDR-заголовок, не требует браузера).

Это отдельный, самостоятельный шаг — не часть переименования/сортировки. Делать его сразу после переименования **не обязательно**, если не просили явно.

## 3. Итоговая последовательность (сверху вниз = порядок действий)

```
1. Сырая картинка
   └─ лежит в assets/sprites/ (корень) или только что загружена
2. Image Prep Tool  ИЛИ  Asset Renamer
   └─ называет по каталогу Object Plan, переносит
3. assets/refs/<id>_<вариация>_<idle|broken|icon>.png
   └─ готовое превью — Object Plan уже видит объект
4. (отдельно, по запросу) копия в assets/sprites/<appearance.asset>
   + appearance.asset / imageWidth / imageHeight / destruction.broken в data/objects/<id>.json
   └─ теперь объект видно в Room Editor / Building Editor / превью ОС
```

Шаги 1→3 — это «разложить и назвать» (то, что обычно и просят). Шаг 4 — это «подключить к игровому объекту», отдельная просьба (мы её выполняли один раз, массово, для 79 объектов при первой генерации каталога — `MD/01-Object-Constructor-OS.md` описывает точную JSON-схему, `collect()`/`restoreJsonFields()` в `tools/os/js/07-object-io.js`).

## 4. GitHub-подключение вместо папки

Все пути выше — относительно **корня репозитория**, не зависят от того, по какому URL открыт сам инструмент (`tools/ipt/...` и т.п.) и не зависят от того, подключена папка проекта или GitHub (`shared/js/github-sync.js`). При GitHub-подключении Image Prep Tool и Asset Renamer пишут туда же (`assets/refs/...`) через Contents API — поведение идентично локальной папке.
