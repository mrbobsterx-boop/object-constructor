# Object Plan — справочник

Приложение-**чек-лист**: список объектов, которые нужно создать в ОС для игры, — зачем каждый нужен, что он делает, какие бывают вариации, какие параметры задать в ОС, с чем он связан и что нужно сделать раньше. Это не редактор: игровых данных приложение не создаёт. Оно только читает проект (для автоматических отметок) и хранит твои отметки о выполненном.

Каталог составлен по дизайн-документу игры и возможностям ОС: **19 разделов, 180 объектов** (P0 — 54, P1 — 92, P2 — 34). Каталог можно править и расширять (см. раздел 6).

Запуск: открыть `object-plan/index.html` в Chrome/Edge. Папку проекта подключать необязательно: без неё работают чек-лист, порядок создания и справочники, отметки хранятся в браузере.

## 1. Разделы приложения

| Раздел | Что показывает |
|---|---|
| **Обзор** | Прогресс (готово / в работе / не начато / отложено), прогресс по приоритетам и разделам, блок «Что делать дальше» — объекты, у которых все требования выполнены (сначала P0) |
| **Чек-лист** | Основной список по разделам: галочка «готово», приоритет, функция, «ждёт / можно», шаги, статус, «найден в проекте». Фильтры: раздел, приоритет, статус, категория ОС, система игры, тип комнаты, «доступные сейчас», поиск |
| **Карточка объекта** | Клик по объекту: статус и заметка; «зачем нужен», функциональная способность, «для чего полезен», открытые вопросы; вариации; блок «как создать в ОС» (поля разложены по вкладкам ОС: русское название поля и английское значение — клик по значению копирует его, у каждой вкладки есть «Копировать вкладку»; свои поля; пояснения); связи; шаги готовности; данные из проекта |
| **Порядок создания** | «Волны» по зависимостям: волна 0 — то, что ни от чего не зависит (материалы, инструменты), затем то, что из них делается. Можно скрыть готовое и оставить только P0 |
| **Сверка с проектом** | Что из плана уже есть в `data/objects`, где расходятся категория и размер, чего не хватает, какие объекты проекта не входят в план (кнопка «Добавить в план») |
| **Справочники** | Категории ОС, разделы, системы, типы комнат (какие объекты нужны для генерации каждого типа), группы взаимозаменяемости (`variant_group`) |
| **Проверки плана** | Целостность самого каталога: битые ссылки, циклы требований, неизвестные словари, пустые поля |
| **Свои объекты** | Форма добавления объекта, которого нет в каталоге; удаление своих объектов |

Шапка: «Подключить папку проекта», «Сверить с проектом», «💾 Прогресс в проект», «📂 Из проекта», «⬇ Чек-лист .md».

## 2. Как отмечать выполненное

Статус объекта — один из: **не начато**, **в работе**, **готово**, **отложено**.

- **Вручную:** галочка в чек-листе или в карточке ставит «готово» (снятие — «не начато»); в карточке есть выбор статуса. Вариант «Авто» снимает ручной статус.
- **По шагам.** У каждого объекта есть шаги готовности (в карточке): картинка, размер и параметры, действия (если они нужны объекту), состояния/анимации (если нужны), рецепт (если объект крафтится), материал блока (для категории «Блок / материал»), сохранён в проект, «используется». Шаг можно отметить вручную. Если статус вручную не задан: все шаги выполнены — «готово», часть — «в работе».
- **По проекту.** После подключения папки шаги определяются автоматически (см. таблицу ниже). Автоматически найденный шаг показан как «✓ найдено в проекте» и отключить его нельзя — он считается по факту.

| Шаг | Автоматически выполнен, если |
|---|---|
| Картинка | у объекта в `data/objects` указана картинка и файл есть в `assets/sprites` |
| Размер и параметры | заданы `behavior.real_width_cm` и `real_height_cm` |
| Действия | у объекта есть `actions[]` |
| Состояния / анимации | в `visuals` есть анимации или картинки-состояния |
| Рецепт | есть `crafting.recipe` |
| Материал блока | у `block` заданы твёрдость и хотя бы одна строка добычи |
| Сохранён в проект | объект с таким id есть в `data/objects` |
| Используется | объект стоит в комнате, лежит блоком в `world.blocks`, входит в набор или на него ссылается другой объект (инструмент, расход, выдача, рецепт, добыча) |

Объект недоступен к началу («ждёт: N»), пока не готовы все объекты из его списка «Сначала создай» (`req`). Отложенные объекты не блокируют других.

## 3. Данные объекта плана

Каждый объект каталога — запись в `js/03…05-data-*.js`:

| Поле | Что значит |
|---|---|
| `id` | id будущего объекта в ОС (a-z, 0-9, `_`, `-`) |
| `n`, `c`, `s` | название, категория ОС, подтип |
| `g` | раздел плана |
| `p` | приоритет: 0 — нужен для первого цикла (бункер → вылазка → возвращение), 1 — расширение, 2 — позже |
| `sz` | рекомендуемый размер, см `[ширина, высота]` |
| `wt` | вес, кг |
| `ph`, `pl` | физика и размещение, если отличаются от умолчаний категории (например, настенные предметы: `STATIC` + `ANYWHERE`) |
| `vg` | группа взаимозаменяемости (`variant_group`) для генерации комнат |
| `why` | **зачем нужен** |
| `fn` | **функциональная способность** — что объект делает в игре |
| `v` | **вариации** |
| `os` | **поля ОС**: ключ — id поля в ОС (`hp`, `lightRadius`, `blockTool`…, список — `OS_FIELDS` в `02-vocab.js`), значение — только английское: enum (`FLOOR_ONLY`), число, id объекта (`tool_pickaxe`). Настройки действия — ключом `ДЕЙСТВИЕ.поле`, например `'HARVEST.produceItem':'veg_potato'`. Добыча блока — `blockDrops:[['stone_chunk',100,1,2]]` (предмет; шанс %; от; до) |
| `cf` | **свои поля** (вкладка «Дополнительно», нет отдельного поля в ОС): `['имя_поля','значение','описание по-русски']`; имя и значение — по-английски |
| `pn` | пояснения по-русски (в ОС не вводятся) |
| `act` | действия ОС, которые нужно включить (`SLEEP`, `OPEN`, `CRAFT`…) |
| `req` | **сначала создай:** материалы рецепта, инструмент, станция или носитель. По ним считаются волны |
| `w` | **с чем взаимодействует.** Обратная связь («с ним взаимодействуют») считается автоматически |
| `use` | **для чего полезен** |
| `rooms` | типы комнат, где объект встречается (для рецептов генерации) |
| `vis` | состояния и анимации, которые нужно нарисовать |
| `sys` | системы игры (вода, энергия, лут, копание…) |
| `rc` | рецепт крафта только из id: `mat_plank ×6 + mat_nails ×10; workbench_basic, tool_hammer` (до `;` — ингредиенты, после — станция и инструмент) |
| `note` | открытые вопросы |

Размер, вес, физика, размещение, группа, действия, состояния, типы комнат и рецепт попадают в поля ОС **автоматически** из полей выше — дублировать их в `os` не нужно.

**Правило языка.** Названия полей ОС показываются по-русски (как в интерфейсе ОС), а все значения, которые копируются в ОС, — по-английски: enum (`RECT`, `CONE`), id объектов, имена состояний, числа с точкой (`0.5`). Исключение одно — «Название» (отображаемое имя объекта). Русскими остаются только описания в `cf`, пояснения `pn` и тексты `why` / `fn` / `use` / `v`. Проверка `OS_LANG` ловит русские значения.

**Важно про ОС.** Значения по умолчанию в ОС: почти все флажки выключены, столкновение `NONE`, физика `STATIC`, размещение `ANYWHERE`. Поэтому в карточке выводится только то, что нужно изменить; чего в списке нет — оставляй как есть. Блок «ресурс» ОС сохраняет только у категорий «Точка ресурса» и «Контейнер»: для других категорий (ванна, ведро, бутылка, машина) ресурс задан свои полями `resource_type` / `resource_max`. Рецепт крафта в ОС — сетка 5×3, одна ячейка = один предмет, поэтому количества из рецепта (`×6`) — это ориентир для баланса, а не число ячеек.

Умолчания физики и размещения по категориям (`CAT_DEFAULTS` в `02-vocab.js`) повторяют поведение ОС: предметы `DYNAMIC` / `ANYWHERE`, мебель, контейнеры, верстаки и машины `DYNAMIC` / `FLOOR_ONLY`, постройки, двери, блоки и растения `STATIC`, персонажи и существа `CHARACTER` / `FLOOR_ONLY`.

Что важно знать о каталоге:
- **Приоритет и требования согласованы.** Объект не может быть приоритетнее того, что нужно для его создания: если P0 требует материал, тот тоже P0 (проверка `PRIORITY_REQ`). Поэтому материалы первого цикла (металлический лист, труба, проволока, ткань, верёвка, электроника, цемент, кувалда и т. п.) имеют приоритет P0.
- **Батарейка и Аккумулятор — разные объекты.** Аккумулятор (`battery_bank`) — контейнер с ресурсом «энергия», стационарный. Батарейка (`battery_cell`) — переносной предмет с ⚙-полем заряда (контейнер в инвентарь не кладётся); в неё вставляют фонарик и ручные приборы.
- **Неразрушаемая порода (`block_bedrock`).** В ОС нет флага «неразрушаем», поэтому в параметрах указана огромная твёрдость (9999); нужно решить, нужен ли явный флаг.
- **Замок и ключ** (`lock_padlock`, `key_generic`) — предметы, но запертость и `key_id` живут в ⚙-полях двери и контейнера; механика замков (см. заметку у шкафчика) пока не решена.
- **Категория «Останки» (`corpse`)** есть в дизайн-документе, но в ОС её нет — объекты помечены «нет в ОС» (проверка `CATEGORY_NEW`). Нужно добавить категорию в ОС (`CAT_LABELS`, кнопки, `STANDARD_ANIMATIONS`) или временно использовать `special`.
- **Хранилища ресурсов** (вода, топливо, энергия) в ОС поддерживают только категории `resource` и `container`, поэтому бочка, резервуар, аккумулятор и канистра описаны как `container`; колодец и куча хлама — как `resource`.
- Расходы, производство энергии, время роста, срок службы и подобные значения в ОС не имеют отдельных полей — они помечены «своё поле» (⚙) и вводятся через «Дополнительно → свои поля».
- Инструменты и материалы старта считаются найденными в мире (`req` пуст), а не скрафченными — иначе получился бы цикл «верстак делается инструментами, а инструменты — на верстаке».

## 5. Хранение отметок

| Где | Что |
|---|---|
| `localStorage['object_plan_v1']` | все отметки: `status`, `steps`, `notes`, `custom` (свои объекты) |
| `data/object_plan.json` | копия отметок в папке проекта — по кнопке «💾 Прогресс в проект» (единственный файл, который пишет приложение); «📂 Из проекта» заменяет отметки в браузере содержимым файла |

Формат `data/object_plan.json`: `{ "schema_version": 1, "saved_at": "…", "status": {"id":"done|wip|todo|skip"}, "steps": {"id":{"image":true}}, "notes": {"id":"текст"}, "custom": [ {объект} ] }`.

«⬇ Чек-лист .md» скачивает весь список с галочками (по разделам) в Markdown.

## 6. Как править каталог

Данные лежат в трёх файлах: `js/03-data-shelter.js` (убежище), `js/04-data-production.js` (производство и строительство), `js/05-data-world.js` (мир, люди, бой). Объект добавляется в конец нужного массива `addItems([...])` с полями из раздела 3. Новые категории, разделы, системы, типы комнат, действия и поля ОС (`OS_FIELDS`, `OS_ENUMS`) — в `js/02-vocab.js`. После правки откройте «Проверки плана»: приложение сообщит о ссылках на несуществующие объекты, циклах и неизвестных значениях словарей. Свои объекты (вкладка «Свои объекты») хранятся вместе с отметками и в каталог не попадают.

## 8. Проверки плана

| Код | Уровень | Что означает |
|---|---|---|
| `ID_DUP`, `ID_SLUG` | err / warn | Повторяется id / id не в формате ОС |
| `CATEGORY`, `GROUP` | err | Категории или раздела нет в словаре |
| `CATEGORY_NEW` | info | Категория ещё не создана в ОС (`corpse`) |
| `REQ_MISSING`, `WITH_MISSING`, `REQ_SELF` | err | `req` / `w` ссылается на несуществующий объект или на себя |
| `PRIORITY_REQ` | warn | Объект приоритетнее того, что нужно для его создания (например, P0 требует материал P1) — материалу нужно поднять приоритет |
| `CYCLE` | err | Цикл в требованиях — волны не определены |
| `SYSTEM`, `ROOM_TYPE`, `ACTION` | warn | Значения нет в словаре / нет в списке действий ОС |
| `NO_WHY`, `NO_FN`, `NO_USE` | warn | Не заполнено описание |
| `NO_VARIANTS`, `NO_SIZE` | info | Нет вариаций / нет рекомендуемого размера |
| `BLOCK_HARDNESS`, `BLOCK_DROPS` | warn / info | У блока не указаны твёрдость или добыча (`blockDrops:[]` — добычи нет намеренно) |
| `OS_KEY`, `OS_ENUM` | err | Неизвестное поле ОС в `os` / значение не из списка ОС (`RECT`, `FLOOR_ONLY`…) |
| `OS_REF` | err | В `os` указан объект (инструмент, добыча, расход, выдача), которого нет в плане |
| `OS_LANG` | warn | Значение поля ОС, своего поля или рецепта написано по-русски — в ОС значения вводятся по-английски |
| `OS_SKILL`, `OS_DROP`, `OS_VALUE`, `OS_ACTION` | warn | Навыка нет среди навыков ОС / шанс вне 0…100 или «от» > «до» / вместо числа строка / настройка действия, которого нет у объекта |
| `OS_RESOURCE_CAT` | warn | Ресурс задан у категории, которая его не сохраняет (только «Точка ресурса» и «Контейнер») |
| `CF_KEY`, `CF_DUP` | warn | Имя своего поля не в формате `a-z_0-9` / повторяется |
| `CF_NOTE` | info | У своего поля нет описания |

## 9. Известные особенности

- Приложение не пишет в `data/objects` и не создаёт объекты — отметки только его собственные.
- Автоматический статус зависит от шагов: если объекту нужны действия или анимации по плану, а в проекте их ещё нет, он останется «в работе», даже если картинка и размер готовы.
- Шаг «Используется» не учитывает лут-таблицы и события (их нет в данных проекта) — такой шаг отмечается вручную.
- Общее число объектов в плане не ограничено, но карточки и связи считаются по id: id объекта плана должен совпадать с id в ОС.
