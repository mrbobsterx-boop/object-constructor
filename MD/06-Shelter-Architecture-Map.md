# Shelter Architecture Map — справочник

Приложение-**чек-лист**, как Object Plan, но не для объектов ОС, а для **Godot-стороны**: что нужно построить в самой игре, чтобы данные из ОС/Room Editor/Building Editor реально стали игрой (скрипты, автозагрузки, UI-компоненты, базовые сцены игровых объектов, Resource-классы под JSON-домены, и отдельно — чек-лист самих сцен комнат/зданий). Это не редактор игровых данных: в `data/objects`, `data/rooms`, `data/buildings` ничего не пишет. Только читает проект (для автоматических отметок и списка сцен) и хранит свои отметки о готовности.

Запуск: `Shelter-Architecture-Map/index.html` в Chrome/Edge. Папку проекта подключать не обязательно: без неё работают четыре авторских каталога, Roadmap и справочники, отметки хранятся в браузере — только раздел «Сцены» и автоматические отметки по путям файлов нуждаются в подключённой папке.

## 1. Пять каталогов чертежа

| Каталог (ключ) | Что в нём | Список берётся из |
|---|---|---|
| Системы (`sys:`) | Автозагружаемые Godot-синглтоны и крупные подсистемы: мост данных (`DataRegistry`, `AssetResolver`, фабрики сцен комнаты/здания), фундамент движка (время, коллизии, навигация, интеракция), персонаж, убежище, мир и сцены, живые NPC, живой мир, последствия, процедурный контент — восемь «слоёв разработки» из мастер-документа | `js/03…06-data-systems-*.js` + свои |
| Компоненты (`comp:`) | Переиспользуемые UI-сцены Godot: атомы, карточки, панели (по одной на игровую механику), оболочка (меню/пауза/настройки) | `js/07-data-components.js` + свои |
| Игровые объекты (`obj:`) | Базовые Godot-сцены/классы — не конкретные предметы из ОС, а классы, которые их инстанцируют, по пяти группам, зеркалящим `CAT_DEFAULTS` ОС: действующие (CHARACTER-физика), переносимые (DYNAMIC+ANYWHERE, carry), расставляемые (DYNAMIC+FLOOR_ONLY), неподвижные (STATIC: постройка/блок/дверь), особые | `js/08-data-gameobjects.js` + свои |
| Данные (`dat:`) | Resource-классы Godot под JSON-домены редакторов: игровые (то, что напрямую становится объектами/комнатами/зданиями) и служебные (настройки, справочники, заготовки редакторов) | `js/09-data-domains.js` + свои |
| Сцены | Комнаты и здания — 1:1 с `data/rooms` и `data/buildings` подключённой папки | **Не авторский**: целиком вычисляется при сканировании проекта (`scanProject()` в `11-store.js`); своего словаря и своих элементов нет |

Четыре авторских каталога — одна и та же форма (раздел 3), общий граф зависимостей (`req` может указывать на элемент **любого** из четырёх каталогов, с префиксом `sys:`/`comp:`/`obj:`/`dat:`) и общий Roadmap по «волнам» постройки. У Сцен своя форма (шаги привязаны к структуре JSON комнаты/здания, а не к `req`) — в общий граф зависимостей они не входят; вместо этого у них отдельный сигнал «рано собирать по-настоящему» (`blockingSystems()`), пока не готовы системы фундамента (`blocksScenes:true`).

## 2. Разделы приложения

| Раздел | Что показывает |
|---|---|
| **Обзор** | Прогресс по четырём авторским каталогам; баннер-блокер, если не готовы системы с `blocksScenes:true`; «Что делать дальше» отдельно по чертежу (первые доступные по волнам, сначала P0) и по сценам; прогресс по восьми слоям разработки |
| **Системы / Компоненты / Игровые объекты / Данные** | Один и тот же рендерер на все четыре (`14-view-catalog.js`, регистрируется 4 раза): список по разделам каталога, фильтры (раздел, приоритет, статус, поиск), карточка элемента — статус, шаги готовности, «зачем нужен» / «что делает», путь файла (`res://…`), автозагрузка (только у систем), связи (`req` и обратная связь «от него зависят»), заметка |
| **Сцены** | Чек-лист комнат и зданий, целиком из подключённого проекта: галочка «готово», шаги готовности по структуре JSON (см. раздел 4), «ждёт: фундамент» если есть незакрытые блокирующие системы |
| **Связи** | Единый граф `req` поверх всех четырёх авторских каталогов сразу — «что использует» / «от чего зависят» |
| **Roadmap** | «Волны» по `req` поверх всех четырёх авторских каталогов одновременно — это и есть чертёж: единый порядок постройки систем, компонентов, игровых объектов и данных, а не по одному списку на каждый каталог |
| **Проект** | Настройка пути к папке сцен Godot (`scenesRoot`, по умолчанию `scenes`); сводка последнего скана: `project.godot` найден/не найден, автозагрузки, каких путей авторских элементов не нашлось, лишние `.tscn` (есть файл — нет id ни в `data/rooms`, ни в `data/buildings`) |
| **Справочники** | Словари каждого каталога (разделы/группы); проверки чертежа (раздел 6); свои элементы — добавить/удалить (в любой из четырёх авторских каталогов) |

Шапка: «📁 Подключить папку проекта», «🔄 Сверить с проектом», «💾 Прогресс в проект», «📂 Из проекта», «⬇ Чертёж .md».

## 3. Как отмечать выполненное

Статус элемента (авторского или сцены) — один из: **не начато**, **в работе**, **готово**, **отложено**.

- **Вручную:** в карточке элемента — выбор статуса. Ручной статус хранится отдельно и перекрывает автоматический; «Авто» его снимает.
- **По шагам.** У каждого каталога свой набор шагов (не общий, в отличие от Object Plan):
  - Системы: скрипт создан по пути, зарегистрирован в Autoload (если нужен), публичный API продуман, подключена к зависимым системам, проверена в игре.
  - Компоненты: `.tscn` создан, скрипт подключён (если нужен), подключён к использующей его панели, проверен в игре с реальными данными.
  - Игровые объекты: базовая `.tscn` создана, скрипт наследует нужный набор компонентов, нужные компоненты подключены, экземпляр создаётся по `object_id` из `DataRegistry`, проверен на реальном объекте из ОС.
  - Данные: формат зафиксирован, Resource-класс создан, загрузчик подключён, проверено на реальных файлах из `data/`.
  - Комнаты: `.tscn` существует, корневой скрипт наследует базовый класс комнаты и берёт данные по id, навигация собрана по зелёным зонам, коллизии — по красным зонам и объектам, объекты заспавнены из `instances[]` через фабрику (шаг показывается только если в комнате есть экземпляры), разрушаемые блоки собраны из `world.blocks` (только если есть блоки), двери подключены к менеджеру переходов (только если есть двери), свет расставлен по данным экземпляров (только если есть источники света), фоновые слои с параллаксом подключены (только если есть фон), сцена пройдена в игре.
  - Здания/улицы: `.tscn` существует, корневой скрипт наследует базовый класс, комнаты собираются по `rooms[]`/`sequence[]`, связи дверей подключены (только если есть `door_links`), RANDOM/POOL слоты резолвятся (только если есть), переключение этажей работает (только если больше одного этажа), фоны подключены (только если есть), пройдено в игре.

  Шаг можно отметить вручную. Если статус вручную не задан: все применимые шаги выполнены → «готово», часть — «в работе».
- **По проекту (автоматически).** После подключения папки и «🔄 Сверить с проектом»:
  - у авторских элементов — шаг «скрипт/сцена/Resource создан» становится готовым, если файл по указанному `path` (`res://…`) реально существует; шаг «зарегистрирован в Autoload» — если имя есть в секции `[autoload]` `project.godot` (по имени синглтона **или** по совпадающему пути, если имя переименовали);
  - у сцен — шаг «`.tscn` существует» становится готовым, если в папке сцен (`scenesRoot`, рекурсивно) есть файл `<id>.tscn`; остальные шаги сцены сейчас отмечаются только вручную (никакой анализ содержимого `.tscn` не делается).

Автоматически найденный шаг нельзя снять вручную — он считается по факту содержимого проекта.

Элемент недоступен к началу («ждёт: N»), пока не готовы все элементы из его `req` (статус не «готово»/«отложено»); отложенные элементы не блокируют других. Дополнительно: пока не готова(-ы) системы с `blocksScenes:true`, на «Обзоре» показывается баннер-блокер, а список «что делать дальше по сценам» скрывается — не то чтобы сцены физически заблокированы (это не входит в граф `req`), это просто напоминание не тратить время на конкретные комнаты, пока не работает фабрика сцен.

## 4. Данные элемента

### Авторский элемент (Системы / Компоненты / Игровые объекты / Данные)

Каждый элемент — запись в `js/03…09-data-*.js`, через `addSystems([...])` / `addComponents([...])` / `addGameObjects([...])` / `addDataDomains([...])`:

| Поле | Что значит |
|---|---|
| `id` | слаг (a-z, 0-9, `_`, `-` — как имя файла Godot) |
| `n` | название |
| `g` | раздел своего каталога (id группы из `SYS_GROUPS`/`UI_GROUPS`/`OBJ_GROUPS`/`DATA_GROUPS`, `02-vocab.js`) |
| `p` | приоритет: 0 (первый игровой цикл), 1 (расширение), 2 (позже) |
| `why` | зачем нужен |
| `fn` | что делает / показывает |
| `path` | предполагаемый путь файла в Godot (`res://…`) — по нему считается автоматический шаг |
| `autoload` | (только у систем) имя синглтона в Project Settings → Autoload, иначе `null` |
| `req` | ключи **других** элементов (любого из четырёх каталогов, с префиксом `sys:`/`comp:`/`obj:`/`dat:`), которые должны быть готовы раньше — по ним считаются волны Roadmap и граф «Связей» |
| `reads` | какие файлы/папки проекта элемент читает — только для смысла (в карточке), в граф зависимостей не идёт |
| `blocksScenes` | (только у систем) без неё собирать сцены «по-настоящему» бессмысленно — даёт баннер-блокер на «Обзоре» |
| `note` | открытый вопрос |

### Сцена (комната или здание/улица)

У сцен нет авторской записи — поля вычисляются при сканировании (`roomToScene()`/`buildingToScene()`, `11-store.js`) прямо из JSON:

| Поле | Источник |
|---|---|
| `widthM`/`heightM`, `instCount`, `doorCount`, `hasLight`, `hasBlocks`, `bgCount`, `compositionRole`, `stairCount` | комната: `widthM/heightM`, `instances[]` (число, есть ли `.door`/`.light`), `world.blocks`, `backgroundLayers`, `compositionRole`, `stairConnections` |
| `layoutMode`, `roomsCount`, `doorLinkCount`, `slotCount`, `floorCount`, `bgCount` | здание: `layout_mode`, `rooms[]`/`sequence[]`, `door_links`, число `RANDOM`/`POOL`-слотов, число этажей (`rooms[].floor`, для «Улицы» всегда 1), `backgroundLayers` |

## 5. Хранение отметок

| Где | Что |
|---|---|
| `localStorage['sam_v1']` | все отметки: `status`, `steps`, `notes`, `custom` (свои элементы по каждому из 4 каталогов), `settings.scenesRoot` |
| `data/scene_plan.json` | копия отметок в папке проекта — по кнопке «💾 Прогресс в проект» (**единственный** файл, который пишет приложение); «📂 Из проекта» заменяет отметки в браузере содержимым файла (с подтверждением) |

Формат `data/scene_plan.json`: `{ "schema_version": 2, "saved_at": "…", "status": {"sys:data_registry":"done"}, "steps": {"key":{"script":true}}, "notes": {"key":"текст"}, "custom": {"system":{},"component":{},"gameobject":{},"data":{}}, "settings": {"scenesRoot":"scenes"} }`.

«⬇ Чертёж .md» скачивает весь список (все 4 авторских каталога по разделам + сцены) с галочками в Markdown.

## 6. Проверки чертежа

Пересчитываются в `checkCatalogs()` (`10-model.js`) при каждой сборке модели; относятся **только** к четырём авторским каталогам (у сцен нет своего словаря/req, поэтому и проверок нет — не считая того, что несуществующий `.tscn` просто не даёт автоматический шаг).

| Код | Уровень | Что означает |
|---|---|---|
| `ID_DUP` | err | id повторяется в своём каталоге (в т.ч. свой элемент повторяет id авторского) |
| `ID_SLUG` | warn | id не в формате `a-z0-9_-` |
| `GROUP` | err | раздела (`g`) нет в словаре этого каталога |
| `NO_WHY`, `NO_FN` | warn | не заполнено «зачем нужен» / «что делает» (не проверяется у своих элементов) |
| `NO_PATH` | info | не указан путь файла (не проверяется у своих элементов) |
| `REQ_MISSING` | err | `req` ссылается на элемент, которого нет ни в одном из четырёх каталогов |
| `REQ_SELF` | err | элемент требует сам себя |
| `CYCLE` | err | элемент участвует в цикле требований — волна не определена |

## 7. Как править каталог

Данные лежат в семи файлах по слоям/разделам: `js/03-data-systems-foundation.js` (слой 1, мост данных + фундамент движка), `js/04-data-systems-character-shelter.js` (слои 2–3), `js/05-data-systems-world-npc.js` (слои 4–5), `js/06-data-systems-livingworld-consequences.js` (слои 6–8: живой мир, последствия, процедурный контент), `js/07-data-components.js`, `js/08-data-gameobjects.js`, `js/09-data-domains.js`. Элемент добавляется в конец нужного вызова `addSystems([...])`/`addComponents([...])`/`addGameObjects([...])`/`addDataDomains([...])` с полями из раздела 4. Новые разделы каталогов и слои разработки — в `js/02-vocab.js` (`SYS_GROUPS`/`UI_GROUPS`/`OBJ_GROUPS`/`DATA_GROUPS`, `LAYERS`). После правки — раздел «Справочники» → «Проверки каталогов» покажет битые `req`, циклы и незаполненные разделы. Свои элементы (кнопка в карточке каталога) хранятся вместе с отметками и в авторский список не попадают, но участвуют в общем графе `req` и Roadmap на равных.

## 9. Известные особенности

- Приложение не пишет в `data/objects`, `data/rooms`, `data/buildings` и не создаёт сцены — отметки только его собственные (`data/scene_plan.json`).
- Автоматический шаг «файл существует» проверяет **только наличие файла по указанному пути**, не его содержимое — Godot-скрипт может существовать и быть пустым, шаг всё равно станет «выполнен».
- У сцен только шаг «`.tscn` существует» автоматический; «объекты заспавнены из instances[] через фабрику», «навигация собрана», «двери подключены» и т.п. — целиком на совести того, кто отмечает вручную (никакого разбора содержимого `.tscn` нет).
- Лишние `.tscn` (файл есть в папке сцен, но нет id ни в `data/rooms`, ни в `data/buildings`) показываются в разделе «Проект» как список, но не как отдельная проверка с кодом — это не обязательно ошибка (сцена может быть не комнатой/зданием — меню, компонент и т. п.).
- `blocksScenes` (у систем) — это не часть графа `req` и не блокирует конкретный элемент: это только предупреждающий баннер на «Обзоре» и скрытие блока «что делать дальше по сценам», ничего не запрещает физически.
- Работает независимо от Character Assembler и Object Plan: не читает и не пишет их файлы, но словарь «Игровых объектов» (`obj:`) описывает классы под категории ОС (в т.ч. `corpse`, которой в ОС пока нет — см. `05-Object-Plan.md`, `CATEGORY_NEW`) и категорию `block` (теперь реализованную в ОС, раздел 1 `01-Object-Constructor-OS.md`).
