# Story Map — справочник

Визуальный конструктор сюжетных узлов и переходов: события, выборы игрока, фоновые (не зависящие от игрока) события, и то, как всё это меняет мир — репутацию фракций, уровень опасности, счётчики дней и любые другие авторские переменные. Узлы группируются по тем же **системам игры**, что уже описаны в Object Plan (`postapocalyptic_survival_master_game_design.md` — оттуда взята вся структура), поэтому граф не превращается в кашу по мере роста. Не редактор игровых данных ОС/Room Editor/Building Editor — отдельный слой, описывающий сюжет и последствия, на основе которого потом пишется код игры и ИИ. Пишет только `data/story.json`. Читает его `story-bot/` (симулятор прохождения, `10-Story-Bot.md`).

Два режима, переключаются кнопками в шапке:
- **📖 Сюжет** — граф узлов/переходов, описанный в §1–§8 ниже.
- **🌍 Мир** — отдельный слой сущностей и типизированных связей между ними (персонажи, локации, фракции… и ссылки на реальные предметы/навыки/действия/системы из Object Plan), §11.

Оба слоя живут в одном `data/story.json` и делят одну историю отмены/возврата (`Ctrl+Z`), но это два разных графа: связи режима «Мир» — строго между сущностями, а не между узлами сюжета, и наоборот.

Запуск: открыть `story-map/index.html` в Chrome/Edge.

---

## 1. Мировые переменные

Авторский список (левая панель, «Мировые переменные»): `id` (генерируется), название, тип (**число** — счётчик типа репутации или уровня опасности; **флаг** — просто да/нет) и начальное значение. Условия и эффекты узлов/переходов ссылаются только на переменные из этого списка — «Проверки» (см. ниже) ловят ссылки на удалённую или ещё не созданную переменную.

## 2. Подключённые каталоги (Object Plan, Shelter Architecture Map)

Story Map подключает вживую два чужих каталога прямо их же скриптами (как `ipt/image-prep-tool` подключает Object Plan) — правишь их там, здесь сразу видно новое, ничего вручную синхронизировать не нужно:

- **Object Plan** (`../object-plan/js/02-vocab.js` + `03-05-data-*.js`) — даёт список предметов (`PLAN_ITEMS`) для поля «Нужны предметы», список навыков (`OS_SKILLS`) для «Нужны навыки» и список **систем игры** (`SYSTEMS`) — это и есть таксономия «разделов», по которым группируются узлы (см. §3).
- **Shelter Architecture Map** — только его каталог систем (`../Shelter-Architecture-Map/js/03…06-data-systems-*.js`), **без** его `02-vocab.js` (там `const PRIORITIES`/`STATUSES` совпадают по именам с Object Plan — загрузка обоих `02-vocab.js` сразу дала бы `SyntaxError`). Вместо этого Story Map сам объявляет `addSystems()`/`SAM_SYSTEM_ITEMS` перед этими файлами — получается тот же список Godot-систем, что видит сам Shelter Architecture Map, только на чтение. Это необязательное поле узла «Система Godot» — обратной связи пока нет: Shelter Architecture Map не читает `data/story.json` (можно добавить позже).

## 3. Узлы

Три вида (влияют только на цвет рамки и подсказки по умолчанию — структура одна и та же): **Событие**, **Выбор** (явное решение игрока), **Фоновое** (срабатывает по таймеру независимо от игрока).

Отдельно от вида — **раздел** (`category`, выпадающий список из `SYSTEMS` Object Plan: вода, энергия, фракции, крафт, ИИ-автономность и т. д.) и **доп. теги** (`tags` — тот же список, можно несколько) — это то, по чему узлы группируются в левой панели (см. §6) и по чему автоматически подключаются импортированные идеи (см. §7). Раздел — один главный, теги — все остальные системы, которых узел тоже касается.

У каждого узла: название, текст (что видит игрок), **когда доступен**:
- **▶ Старт** — доступен сразу, с него начинается игра (должен быть ровно один такой узел — иначе «Проверки» пожалуются).
- **⚑ По условиям** — список условий (переменная / знак `≥ ≤ = ≠ > <` / число), все должны выполняться.
- **⏱ Фоновое, по таймеру** — срабатывает само через N игровых часов после старта игры или после того, как сработал другой указанный узел; можно включить «повторять».

**Что меняет при срабатывании** — список эффектов (переменная / `= + −` / число).

**Параметры для бота-симулятора**: длительность в игровых часах, шанс опасности (0…1), расход еды/воды (**отрицательное число — восполняет**, например «поесть»), **нужны предметы** / **нужны навыки** — фишки с автодополнением, значения берутся из `PLAN_ITEMS`/`OS_SKILLS` (см. §2): начни печатать название в поле рядом — подставится из списка; если совпадения нет, фишка всё равно добавится как есть (не блокирует ввод).

**Концовка** — если заполнено (например `death`, `victory`, своя строка), узел считается финалом.

## 4. Переходы (связи)

Два способа создать: **потянуть за кружок** на правом краю узла на холсте до другого узла (отпустишь на пустом месте холста — там же создастся новый узел и сразу с ним свяжется), или кнопкой «+ добавить переход» в инспекторе. У каждого перехода — текст, целевой узел, свои «Требуется» и «Меняет» (в дополнение к узловым). До трёх переходов показываются прямо на теле узла на холсте (со стрелкой `↳`), остальные — только счётчиком «→ N».

**Выбор нескольких узлов и групповые операции**: Ctrl/Shift+клик по узлу на холсте (или в списке слева) добавляет его к выбору; `Shift`+перетаскивание пустого места холста — рамка выделения (обычное перетаскивание без Shift — панорама); `Ctrl+A` — выбрать все узлы. Перетаскивание любого узла из текущего выделения двигает всю группу разом, сохраняя относительное расположение. `Delete`/`Backspace` удаляет весь выбор (с подтверждением). `Ctrl+C`/`Ctrl+V` копирует выделенные узлы: переходы между узлами **внутри** выделения переносятся и переиндексируются на новые id, переходы **наружу** — отбрасываются (вставленная копия не тянет невидимых нитей к оригиналу); если среди скопированного был узел со стартовым триггером, его копия автоматически становится обычным условным узлом (второго старта быть не может).

## 5. Проверки

Список кликабелен: клик по любой проблеме, у которой есть привязка к узлу, выделяет и центрирует этот узел на холсте — «Проверки» это инструмент навигации, а не просто текст. Сверху — сводка (сколько узлов/переменных/концовок/узлов без входящих переходов).

| Проблема | Смысл |
|---|---|
| Нет стартового узла | Ни один узел не отмечен «▶ Старт» |
| Стартовых узлов несколько (err) | Игра не может начинаться сразу из двух точек |
| Ссылается на несуществующую переменную | Условие/эффект использует id переменной, которой нет в списке |
| Переход ведёт в несуществующий узел | `target` перехода не совпадает ни с одним id узла |
| Отсчёт таймера от несуществующего узла | `sinceNode` фонового узла не существует |
| Шанс опасности вне 0…1 (warn) | `sim.dangerChance` должен быть долей, не процентом и не отрицательным |
| Нет текста (info) | У узла пусто поле «Текст» — игрок ничего не увидит |
| Переменная не используется (warn) | Ни в одном условии/эффекте нет ссылки на неё |
| min больше max (warn) | У переменной перепутаны границы |
| Тупик без развития (info) | У узла нет ни переходов, ни отметки концовки |
| Нет входящих переходов (info) | **Не то же самое, что «недостижим»**: узел без входящих переходов, который не старт и не фоновый, может быть либо забыт, либо намеренно активируется только своим условием (зависит от мировых переменных, а не от того, что на него кто-то сослался переходом) — это структурная, а не «во время игры» проверка |
| Ссылка каталожной сущности не найдена (warn) | `ref.refId` сущности слоя «Мир» больше не встречается в загруженном каталоге Object Plan — переименовали/удалили там |
| Связь ссылается на несуществующую сущность (err) | `from`/`to` связи не совпадает ни с одним id сущности |
| Неизвестный тип связи (err) | `type` связи не совпадает ни с одним id из списка «Типы связей» |

Панель «Проверки» — общая для обоих слоёв и видна **в обоих режимах** (лежит вне `storyLeftPanels`/`worldLeftPanels`, ниже них), не нужно переключаться на «📖 Сюжет», чтобы увидеть ошибку в связи, найденную во время правки «Мира».

## 6. Левая панель: узлы по разделам, поиск, сужаемая ширина

Список узлов сгруппирован по `category`: заголовок раздела (кликабельный — сворачивает/разворачивает список внутри, для больших графов), под ним — узлы этого раздела, каждый с одной строкой «→ на что влияет» (имена переменных из его собственных эффектов и эффектов его переходов). Клик по узлу открывает его в инспекторе **и** центрирует холст на нём, **сохраняя текущий масштаб** (резкого скачка нет). Над списком — поиск (по названию, тексту, id, разделу/тегам и именам связанных переменных) и два фильтра (тип, статус: тупики / концовки / без входящих переходов).

Границу между левой панелью и холстом можно тянуть мышкой (курсор `col-resize`) — панель становится шире или уже.

`⛶ Fit all` в шапке подгоняет масштаб и сдвиг так, чтобы весь граф был виден целиком — полезно после импорта идеи или когда узлов уже много. В правом нижнем углу холста — миникарта (цветные прямоугольники по типу узла, белая рамка — текущая видимая область); клик по ней переносит холст в это место.

`🔦 Фокус` рядом с «Fit all» — переключатель «режима фокуса»: пока он включён и выбран узел, холст подсвечивает только его саму и всё, до чего можно дойти по переходам **вперёд** (обычный обход в ширину по `choices`), а всё остальное (узлы и связи) притушивает. Полезно проследить один путь в разросшемся графе, не отвлекаясь на параллельные ветки; переключение узла или повторный клик по кнопке сразу пересчитывают подсветку.

## 7. Импорт идей — универсальный JSON-шаблон

Одна идея — самостоятельный кусок сюжета в отдельном JSON-файле: свои узлы (с **локальными** `ref` вместо настоящих id — они одноразовые, только чтобы сослаться друг на друга внутри этого же файла), свои новые переменные, явные **links** — с какими уже существующими узлами (по разделу или тегу) новые узлы должны связаться — и, отдельно, сущности/связи/идеи для слоя «Мир» (§11). Кнопки в левой панели («Импорт идей»): «⬇ Шаблон идеи» скачивает рабочий пример (NPC сам подсказывает донести аккумулятор + пример сущностей/связей DRINK→эффект), «📥 Импорт идеи (JSON)» — открывает файл.

Импорт идёт в два шага — **Анализ → Превью → Слияние**, не сразу: выбор файла считает (не трогая граф) сколько узлов/переменных/сущностей/связей добавится и что из этого уже совпадает с существующим, и показывает окно-подтверждение; граф меняется только по кнопке «Добавить в граф» в этом окне (кнопка «Отмена» просто закрывает превью, ничего не тронув). Числа в превью и то, что реально добавится при подтверждении — гарантированно одни и те же (`analyzeIdea()` и `importIdea()` используют одну и ту же логику сопоставления «новое/уже есть», а не отдельную прикидку на глаз).

Импорт **только добавляет**: переменные с уже существующим id пропускаются (не перезаписываются), узлы никогда не удаляются, а `links` ищутся по **текущему**, уже пополненному списку узлов — поэтому если сегодня ты импортируешь идею про фракции, а завтра другую идею, тоже помеченную тегом `factions`, она сама подключится и к старым узлам, и к тем, что добавила первая идея. Это не «ИИ понимает смысл» — это прямое совпадение по `match_category`/`match_tag`, которые сам указываешь в файле; надёжно и предсказуемо, зато не обещает большего, чем может. Сущности из бандла точно так же не дублируются: авторская сущность (без каталога) считается той же при совпадении вида+имени (без учёта регистра), каталожная — при совпадении вида+ссылки на каталог; типы связей, которых ещё нет в списке, создаются автоматически.

Формат файла:

```jsonc
{
  "idea_id": "npc_self_hint_example",           // просто метка для журнала импортов
  "title": "NPC сам подсказывает, чего не хватает",
  "variables": [                                 // новые мировые переменные (пропускаются, если id уже есть)
    {"id":"v_electricity_home","name":"Электричество в доме","type":"flag","start":0,"min":0,"max":1}
  ],
  "nodes": [
    {
      "ref": "n1",                               // локальная ссылка, только для этого файла
      "title": "NPC: намёк про свет",
      "text": "«Темновато тут. Если бы был аккумулятор — я бы свет наладил.»",
      "type": "background", "category": "ai", "tags": ["energy","story"],
      "trigger": {"kind":"scheduled","afterHours":24,"sinceNode":"","repeat":true},
      "effects": [],
      "sim": {"durationHours":0,"dangerChance":0,"foodCost":0,"waterCost":0,"requiresItems":[],"requiresSkills":[]},
      "ending": "",
      "choices": [
        {"label":"Занести аккумулятор","target_ref":"n2","requires":[],
         "effects":[{"var":"v_electricity_home","op":"set","value":1}],"sim":{"requiresItems":["battery_cell"]}}
      ]
    },
    {"ref":"n2","title":"Свет в доме включён","text":"NPC радуется.",
     "type":"event","category":"energy","tags":["ai"],
     "trigger":{"kind":"conditions","all":[]},"effects":[],"sim":{},"ending":"","choices":[]}
  ],
  "links": [
    // от узла n2 — ко ВСЕМ текущим узлам с тегом "energy" (кроме себя), в обе идеи-импорта одинаково
    {"from_ref":"n2","match_tag":"energy","label":"(связано: тоже про энергию)"}
    // или "match_category":"energy" вместо match_tag — тогда сравнивается основной раздел узла, а не доп. теги
  ],

  // Необязательно — сущности/связи/идеи для слоя "Мир" (§11), тот же приём с локальным "ref".
  // kind без каталога (character/location/faction/group/concept/resource/effect/animation) —
  // "name" свободным текстом; kind с каталогом (item/skill/action/system) — "refId" реальным
  // id/строкой из Object Plan (PLAN_ITEMS/OS_SKILLS/ACTIONS/SYSTEMS).
  "entities": [
    {"ref":"e_ivan","kind":"character","name":"Иван"},
    {"ref":"e_drink","kind":"action","refId":"DRINK"},
    {"ref":"e_thirstfix","kind":"effect","name":"Восстановление жажды"}
  ],
  "relations": [
    // "type" — свободное имя типа связи: если такого ещё нет в списке типов, он создастся сам
    {"from_ref":"e_ivan","type":"can_perform","to_ref":"e_drink","status":"confirmed","comment":"Иван может пить"},
    {"from_ref":"e_drink","type":"produces","to_ref":"e_thirstfix","status":"confirmed"}
  ],
  "proposals": [
    {"title":"Завести Need-сущность \"Голод\" по аналогии с жаждой","text":"см. design doc"}
  ]
}
```

`target_ref` внутри `choices` ссылается на `ref` из этого же файла (превращается в настоящий id при импорте); можно вместо этого указать `target` с настоящим id уже существующего узла напрямую, если он тебе известен. Узлы новой идеи раскладываются по «слоям» (глубина = кратчайший путь от корня бандла по `target_ref`) слева направо, ниже уже существующего содержимого — так большинство связей идут вперёд, а не петляют, и их несложно донастроить перетаскиванием после импорта.

`links[]` по умолчанию подключается ко **всем** текущим совпадениям (без дублей — одна и та же пара «откуда-куда» не создаётся дважды даже при повторном импорте того же файла) и с потолком в 30 автосвязей на один `link` за один импорт (если тег слишком общий и совпадений больше — остаток можно добрать повторным импортом или сузив тег; в консоль браузера пишется предупреждение). Добавь `"mode":"first"` в `link`, чтобы подключиться только к первому совпадению, а не ко всем.

## 8. Хранение и формат

Пишет только `data/story.json`: `{schema_version, variables:[{id,name,type,start,min,max}], nodes:[{id,title,text,type,category,tags,samSystem,x,y,trigger,effects,sim,choices,ending}], entities:[{id,kind,name,ref,note}], relationTypes:[{id,name}], relations:[{id,type,from,to,status,source,comment,conditions,effects}], proposals:[{id,title,text,status,relatedEntities,relatedSystems}]}`, где `sim.requiresItems`/`sim.requiresSkills` — массивы id (а не текст). Файлы, сохранённые до этого раздела (без `category`/`tags`/массивов requires, или вообще без `entities`/`relationTypes`/`relations`/`proposals`), читаются как раньше — везде подставляются пустые массивы/значения по умолчанию, если поля в файле нет; при первой загрузке (или если файл не содержит своих `relationTypes`) список типов связей заполняется словарём по умолчанию (`member_of`, `located_at`, `contains`, `owns`, `can_perform`, `uses`, `produces`, `satisfies_need`, `has_skill`, `has_need`, `is_a`, `supports`, `friend_of`, `enemy_of`) — его можно редактировать и дополнять как обычный список. `Ctrl+Z`/`Ctrl+Shift+Z` — отмена/возврат (общая история правок для обоих слоёв, в браузере, не файла на диске).

Шапка показывает, есть ли несохранённые изменения («● Есть несохранённые изменения» / «✓ Сохранено»); `Ctrl+S` сохраняет так же, как кнопка «💾 Сохранить». Попытка закрыть или перезагрузить вкладку с несохранёнными изменениями показывает стандартное предупреждение браузера.

Каждое сохранение сначала читает то, что прямо сейчас лежит в `data/story.json`, и, если там что-то есть, копирует это как есть в `data/story.backup.json` — только потом пишет новую версию поверх `story.json`. Бэкап один (не журнал версий): хранит ровно предыдущее сохранение, обновляется каждый следующий раз. На самом первом сохранении в новой папке бэкапить ещё нечего — файла не будет, это нормально. Сама запись каждого файла атомарна «бесплатно» — так работает File System Access API (пишет во временный файл, подменяет им целевой только при закрытии потока), поэтому обрыв соединения/скрипта посреди сохранения не может оставить `story.json` наполовину переписанным.

## 11. Режим «Мир»: сущности, связи, идеи-предложения

Второй слой поверх графа сюжета — не сюжетные узлы, а **сущности игрового мира** и типизированные связи между ними, отдельный граф со своими checks, своим импортом и своей правой панелью (общей физически с инспектором узла, но занятой либо тем, либо другим — режимы взаимоисключающие).

**Сущность** (`kind`, `name`/`ref`, `note`) бывает:
- **авторской** — персонаж, локация, фракция, группа, концепт, ресурс, эффект, анимация: имя — свободный текст, ничего не каталогизировано;
- **каталожной** — предмет/навык/действие/система: не дублирует Object Plan, а **ссылается** на него (`ref.refId`) — выпадающий список берётся прямо из уже загруженных `PLAN_ITEMS`/`OS_SKILLS`/`ACTIONS`/`SYSTEMS` (§2); если запись в каталоге переименуют или удалят, «Проверки» это заметят (см. §5).

Левая панель («Сущности», «Идеи / предложения», «Типы связей»): выбор вида + «+ добавить» создаёт сущность (для каталожных видов автоматически берётся первая ещё не занятая запись каталога — поменять можно потом в карточке сущности), поиск фильтрует список (по имени/виду/заметке), список сгруппирован по виду с заголовками-счётчиками. «Идеи / предложения» — вольный текст идеи без структуры («завести систему Х», «а что если Y») со статусом (идея/принято/отклонено); клик по идее в списке предлагает сделать её сущностью выбранного в селекторе слева вида (`promoteProposalToEntity`) — сама идея остаётся в списке с отметкой «принято». «Типы связей» — авторский редактируемый список (как переменные в §1), с несколькими типами по умолчанию (см. §8); связь всегда ссылается на id из этого списка, а не на голую строку — поэтому переименование типа сразу применяется ко всем связям этого типа.

Центральная область — карточка выбранной сущности: поле имени (или выбор из каталога для каталожных видов) + заметка, и список её связей — **обеих сторон** сразу (`→` — эта сущность источник, `←` — эта сущность цель), с типом связи и именем другой сущности; клик по имени другой сущности переключает карточку на неё (тот же принцип «клик по ветке — перейти к ней», что и `focusNode()` в §6); «✕» удаляет отдельную связь, «+ добавить связь» создаёт черновую связь от текущей сущности и сразу открывает её в редакторе справа. Удаление сущности удаляет и все связи, где она участвует (как удаление узла обрывает переходы на него, §4).

Правая панель в режиме «Мир» — редактор выбранной связи: `от`/`тип`/`к` (все три — выпадающие списки: сущности и типы связей), статус (подтверждено / предположение / устарело), источник (свободный текст — например `idea:bunker_start` или имя design-документа), комментарий, и (тем же общим устройством условий/эффектов, что у узлов и переходов, §3–4) **условия** — когда связь считается действующей — и **эффекты** — что она меняет при срабатывании.
