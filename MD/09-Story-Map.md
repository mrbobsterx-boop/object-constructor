# Story Map — справочник

Визуальный конструктор сюжетных узлов и переходов: события, выборы игрока, фоновые (не зависящие от игрока) события, и то, как всё это меняет мир — репутацию фракций, уровень опасности, счётчики дней и любые другие авторские переменные. Узлы группируются по тем же **системам игры**, что уже описаны в Object Plan (`postapocalyptic_survival_master_game_design.md` — оттуда взята вся структура), поэтому граф не превращается в кашу по мере роста. Не редактор игровых данных ОС/Room Editor/Building Editor — отдельный слой, описывающий сюжет и последствия, на основе которого потом пишется код игры и ИИ. Пишет только `data/story.json`. Читает его `story-bot/` (полноценный бот-симулятор прохождения, `10-Story-Bot.md`) — а для быстрой проверки логики прямо здесь, без переключения в другой инструмент, есть лёгкий inline-прогон «▶ Играть» (§18), который его не заменяет.

Три режима, переключаются кнопками в шапке:
- **📖 Сюжет** — граф узлов/переходов, описанный в §1–§9 ниже.
- **🌍 Мир** — отдельный слой сущностей и типизированных связей между ними (персонажи, локации, фракции… и ссылки на реальные предметы/навыки/действия/системы из Object Plan), §12.
- **🕐 Таймлайн** — те же узлы сюжета под другим углом: только те, у кого есть определённый момент в игровом времени, в хронологическом порядке — не отдельный граф и не редактор, просто ещё один способ посмотреть на то же самое, §17.

«Мир» — отдельный граф (связи там строго между сущностями, а не между узлами сюжета, и наоборот), «Таймлайн» — вообще не граф, а альтернативное представление узлов «Сюжета». Все живут в одном `data/story.json` и делят одну историю отмены/возврата (`Ctrl+Z`).

Запуск: открыть `story-map/index.html` в Chrome/Edge.

## 1. Мировые переменные

Авторский список (левая панель, «Мировые переменные»): `id` (генерируется), название, тип (**число** — счётчик типа репутации или уровня опасности; **флаг** — просто да/нет) и начальное значение. Условия и эффекты узлов/переходов ссылаются только на переменные из этого списка — «Проверки» (см. §5) ловят ссылки на удалённую или ещё не созданную переменную.

**Dependency Explorer** — кнопка «🔗» у переменной разворачивает под её строкой две колонки: «Меняют» (все эффекты узлов/переходов/связей мира, которые её трогают, с самим действием — `=`/`+`/`−` и значением) и «Читают» (все условия, которые её проверяют, со знаком и значением). Раскрыта не больше одной переменной за раз — те же узлы, что участвуют в списках, одновременно подсвечиваются на холсте пунктирной рамкой, чтобы видеть их в контексте графа, а не только по названию. Клик по строке в любой из колонок выделяет и центрирует соответствующий узел (или, если это связь мира — переключает на режим «Мир» и открывает её в редакторе связи). Открывается либо самой кнопкой «🔗», либо кликом по «Проверкам», у которых problem относится именно к переменной (см. §5).

## 2. Подключённые каталоги (Object Plan, Shelter Architecture Map)

Story Map подключает вживую два чужих каталога прямо их же скриптами (как `ipt/image-prep-tool` подключает Object Plan) — правишь их там, здесь сразу видно новое, ничего вручную синхронизировать не нужно:

- **Object Plan** (`../object-plan/js/02-vocab.js` + `03-05-data-*.js`) — даёт список предметов (`PLAN_ITEMS`) для поля «Нужны предметы», список навыков (`OS_SKILLS`) для «Нужны навыки» и список **систем игры** (`SYSTEMS`) — это и есть таксономия «разделов», по которым группируются узлы (см. §3).
- **Shelter Architecture Map** — только его каталог систем (`../Shelter-Architecture-Map/js/03…06-data-systems-*.js`), **без** его `02-vocab.js` (там `const PRIORITIES`/`STATUSES` совпадают по именам с Object Plan — загрузка обоих `02-vocab.js` сразу дала бы `SyntaxError`). Вместо этого Story Map сам объявляет `addSystems()`/`SAM_SYSTEM_ITEMS` перед этими файлами — получается тот же список Godot-систем, что видит сам Shelter Architecture Map, только на чтение. Это необязательное поле узла «Система Godot» — обратной связи пока нет: Shelter Architecture Map не читает `data/story.json` (можно добавить позже).

## 3. Узлы

Три вида (влияют только на цвет рамки и подсказки по умолчанию — структура одна и та же): **Событие**, **Выбор** (явное решение игрока), **Фоновое** (срабатывает по таймеру независимо от игрока).

Отдельно от вида — **раздел** (`category`, выпадающий список из `SYSTEMS` Object Plan: вода, энергия, фракции, крафт, ИИ-автономность и т. д.) и **доп. теги** (`tags` — тот же список, можно несколько) — это то, по чему узлы группируются в левой панели (см. §6) и по чему автоматически подключаются импортированные идеи (см. §8). Раздел — один главный, теги — все остальные системы, которых узел тоже касается.

У каждого узла: название, текст (что видит игрок), **когда доступен**:
- **▶ Старт** — доступен сразу, с него начинается игра (должен быть ровно один такой узел — иначе «Проверки» пожалуются).
- **⚑ По условиям** — список условий (переменная / знак `≥ ≤ = ≠ > <` / число), все должны выполняться.
- **⏱ Фоновое, по таймеру** — срабатывает само через N игровых часов после старта игры или после того, как сработал другой указанный узел; можно включить «повторять».

**Что меняет при срабатывании** — список эффектов (переменная / `= + −` / число).

**Параметры для бота-симулятора**: длительность в игровых часах, шанс опасности (0…1), расход еды/воды (**отрицательное число — восполняет**, например «поесть»), **нужны предметы** / **нужны навыки** — фишки с автодополнением, значения берутся из `PLAN_ITEMS`/`OS_SKILLS` (см. §2): начни печатать название в поле рядом — подставится из списка; если совпадения нет, фишка всё равно добавится как есть (не блокирует ввод).

**Концовка** — если заполнено (например `death`, `victory`, своя строка), узел считается финалом.

**Связано с миром** (вкладка «Ссылки» в инспекторе, `node.refs`) — узел может сослаться на конкретные сущности режима «Мир» (персонаж, локация, фракция, предмет и т. д., §12) вместо того, чтобы упоминать их только текстом. Это именно **ссылка**, не копия: имя сущности всегда читается из «Мира», редактировать саму сущность (переименовать, сменить каталожную привязку, дописать заметку) нужно там же — узел лишь помнит, что она в нём участвует. Фишки-пикер, как у тегов/предметов/навыков (§2), но кликабельный: клик по имени фишки (не по «✕») переключает на режим «Мир» и открывает эту сущность — а на её карточке в «Мире» видно обратный список «Упоминается в сюжете» с переходом назад к узлу (см. §12). «Проверки» (§5) ловят ссылку на сущность, которую с тех пор удалили.

Кнопки «+ Событие / + Выбор / + Фоновое» в левой панели ставят новый узел **справа от текущего** — от выбранного узла, а если выбора нет, от последнего добавленного, а не в одну и ту же фиксированную точку холста. Новый узел сразу становится выбранным, поэтому несколько кликов подряд выстраиваются цепочкой слева направо, а не грудой друг на друге. Явные координаты (перетаскивание соединения на пустое место §4, вставка Ctrl+V, импорт идеи §8, вставка шаблона сцены §17) этим правилом не затрагиваются — ставят узел ровно туда, куда и раньше.

**Арка / Глава** — необязательные поля свободного текста (вкладка «Основное»): чисто навигационная группировка узлов, не меняющая сам граф и не видная боту-симулятору (§17) — не путать с **разделом** выше, который берётся из закрытого каталога Object Plan и определяет цвет/группировку по игровым системам.

**Источник события** (`node.eventSource`, вкладка «Основное») — необязательная авторская пометка «кто/что это инициирует» (Игрок / NPC / Фракция / Мир / Локация / Таймер / Игровая система), видна значком рядом с названием в списке слева и на холсте. Не влияет на срабатывание узла — это не то же самое, что **«когда доступен»** выше (старт/по условиям/по таймеру, который решает МЕХАНИКУ появления узла); `eventSource` описывает смысловой источник, а «когда доступен» — механизм, и они сознательно не объединены в один общий enum (§19).

## 4. Переходы (связи)

Два способа создать: **потянуть за кружок** на правом краю узла на холсте до другого узла (отпустишь на пустом месте холста — там же создастся новый узел и сразу с ним свяжется), или кнопкой «+ добавить переход» в инспекторе. У каждого перехода — текст, целевой узел, свои «Требуется» и «Меняет» (в дополнение к узловым). До трёх переходов показываются прямо на теле узла на холсте (со стрелкой `↳`), остальные — только счётчиком «→ N».

Кнопка «🔗» у перехода разворачивает **возможную цепочку последствий** этого выбора (§20) — куда дальше могут докатиться его эффекты через переменные, которые читают другие узлы.

Если несколько узлов оказались перекрыты друг другом на холсте (плотная цепочка, только что вставленные копии со сдвигом и т.п.), отпускание соединения ищет цель среди перекрывающих узел под курсором, а не только самый первый — берётся визуально верхний, и сам источник соединения никогда не считается целью самому себе.

**Выбор нескольких узлов и групповые операции**: Ctrl/Shift+клик по узлу на холсте (или в списке слева) добавляет его к выбору; `Shift`+перетаскивание пустого места холста — рамка выделения (обычное перетаскивание без Shift — панорама); `Ctrl+A` — выбрать все узлы. Перетаскивание любого узла из текущего выделения двигает всю группу разом, сохраняя относительное расположение. `Delete`/`Backspace` удаляет весь выбор (с подтверждением). `Ctrl+C`/`Ctrl+V` копирует выделенные узлы: переходы между узлами **внутри** выделения переносятся и переиндексируются на новые id, переходы **наружу** — отбрасываются (вставленная копия не тянет невидимых нитей к оригиналу); если среди скопированного был узел со стартовым триггером, его копия автоматически становится обычным условным узлом (второго старта быть не может).

## 5. Проверки

Список — инструмент навигации, а не просто текст: клик по проблеме с привязкой к узлу выделяет и центрирует его на холсте; с привязкой к сущности мира — переключает на «Мир» и открывает её; с привязкой к переменной (и без привязки к узлу) — раскрывает Dependency Explorer этой переменной (§1) и прокручивает к ней. Сверху — сводка **Ошибок / Предупреждений / Инфо** (по счётчику каждого уровня), затем те же общие цифры, что и раньше (узлов/переменных/концовок/без входящих переходов/сущностей/связей).

**Graph Reachability vs Runtime Availability** — сознательно разделены, это разные вопросы:
- **Reachability** («есть ли структурный путь до узла») — то, что было и раньше: BFS по `choices` от старта/фоновых узлов.
- **Runtime Availability** («может ли условие само по себе когда-нибудь стать истинным») — новый, отдельный анализ. Узел может быть недостижим по путям, но иметь совершенно исправное условие (ждёт мировую переменную, которую меняет что-то другое); и наоборот — до узла может вести переход, но его собственное условие никогда не выполнится ни при каком течении игры. Не одно и то же, и «Проверки» больше не путают эти два вопроса.

| Проблема | Уровень | Смысл |
|---|---|---|
| Нет стартового узла | err | Ни один узел не отмечен «▶ Старт» |
| Стартовых узлов несколько | err | Игра не может начинаться сразу из двух точек |
| Одинаковый id узла/переменной у нескольких записей | err | Целостность данных — обычно только после ручной правки JSON или неудачного слияния файлов; ссылки на такой id становятся неоднозначными |
| Ссылается на несуществующую переменную | err | Условие/эффект использует id переменной, которой нет в списке |
| Переход ведёт в несуществующий узел | err | `target` перехода не совпадает ни с одним id узла |
| Отсчёт таймера от несуществующего узла | err | `sinceNode` фонового узла не существует |
| **Условие вне объявленного диапазона переменной** | err | Runtime Availability: например условие «репутация ≥ 150», когда у переменной `max=100`, — невозможно ни при каких эффектах, диапазон переменной сам это исключает |
| **Условие никогда не станет истинным** | err | Runtime Availability: ничто в графе (ни один эффект — узла, перехода или связи мира) не меняет эту переменную, а стартовое значение условию не удовлетворяет |
| **Несколько условий в одном списке взаимно исключают друг друга** | err | Например «репутация ≥ 60» и «репутация < 30» в одном `AND`-списке — такой список не выполнится никогда, порознь оба условия могли бы быть верными, вместе — нет |
| Шанс опасности вне 0…1 | warn | `sim.dangerChance` должен быть долей, не процентом и не отрицательным |
| Переменная нигде не используется | warn | Ни в одном условии/эффекте нет ссылки на неё |
| **Переменная меняется, но нигде не проверяется** | info | Возможно, задел на будущее — не обязательно ошибка |
| **Переменная проверяется условием, но ничто её не меняет** | warn | Если стартовое значение само по себе не устраивает условие, оно никогда не сработает иначе |
| min больше max | warn | У переменной перепутаны границы |
| Тупик без развития | warn (было info) | У узла нет ни переходов, ни отметки концовки (и он не изолирован полностью — см. ниже); почти всегда забытая ветка — если это финал, впиши что-нибудь в поле «Концовка», тогда пункт не появится вовсе (§19) |
| **Полностью изолирован** | info | Ни входящих, ни исходящих переходов, ни отметки концовки одновременно — сообщается один раз вместо трёх разных сообщений про то же самое |
| **Несколько переходов в один и тот же узел** | info | С одного узла — два (и более) перехода к одной цели; не обязательно ошибка (разные варианты одной и той же встречи), но стоит взглянуть |
| **Цикл** | info | Обнаружен путь, возвращающийся сам к себе через уже пройденный узел (DFS, обратные рёбра) — нормально для survival-петель («сходить к колодцу и вернуться»), просто для осознанности |
| Нет входящих переходов (Reachability) | info | **Не «недостижим» в смысле логики**: узел без входящих переходов, который не старт и не фоновый, может быть либо забыт, либо намеренно активируется только своим условием — это структурный вопрос, Runtime Availability проверяется отдельными пунктами выше |
| Ссылка каталожной сущности не найдена | warn | `ref.refId` сущности слоя «Мир» больше не встречается в загруженном каталоге Object Plan — переименовали/удалили там |
| Связь ссылается на несуществующую сущность | err | `from`/`to` связи не совпадает ни с одним id сущности |
| Неизвестный тип связи | err | `type` связи не совпадает ни с одним id из списка «Типы связей» |
| Ссылка узла на сущность мира не найдена | warn | `node.refs` (вкладка «Ссылки», §3) указывает на сущность, которую с тех пор удалили в режиме «Мир» |
| Ссылка «Действие»/«Цель» не найдена | warn | `node.actionRef.action`/`.target` (§21) указывает на сущность, которую с тех пор удалили в режиме «Мир» |
| Сущность нигде не используется | info | Ни в `node.refs`/`actionRef`, ни в связях, ни в идеях-предложениях — забыта или задел на будущее (§22, «Orphan Detection») |

Пункты **выделенные жирным** — новые в этом раунде (граф-целостность + Runtime Availability + переработанная навигация). Контрадикция проверяется через интервальную арифметику по `>=`/`<=`/`>`/`<`/`==` (`!=` намеренно не сужает интервал — чтобы не давать ложных срабатываний); «эффект делает более позднюю ветку недостижимой» (пункт бэклога — см. `11-Story-Map-Backlog.md`, группа G) сознательно не реализован — для этого пришлось бы моделировать порядок применения эффектов во времени по всем ветвлениям графа, что either требует полноценного перебора состояний, либо даёт ненадёжные ложные срабатывания; честнее было не делать этого, чем сделать плохо.

Панель «Проверки» — общая для всех режимов и видна **во всех трёх** (лежит вне `storyLeftPanels`/`worldLeftPanels`, ниже них), не нужно переключаться на «📖 Сюжет», чтобы увидеть ошибку в связи, найденную во время правки «Мира», или разглядывая «Таймлайн».

## 6. Левая панель: узлы по разделам, поиск, сужаемая ширина

Список узлов сгруппирован по `category`: заголовок раздела (кликабельный — сворачивает/разворачивает список внутри, для больших графов), под ним — узлы этого раздела, каждый с одной строкой «→ на что влияет» (имена переменных из его собственных эффектов и эффектов его переходов). Клик по узлу открывает его в инспекторе **и** центрирует холст на нём, **сохраняя текущий масштаб** (резкого скачка нет). Над списком — поиск (по названию, тексту, id, разделу/тегам, арке/главе и именам связанных переменных) и четыре фильтра (тип, статус: тупики / концовки / без входящих переходов, арка, глава — последние два собираются из того, что реально уже встречается в графе, §17).

Границу между левой панелью и холстом можно тянуть мышкой (курсор `col-resize`) — панель становится шире или уже.

`⛶ Fit all` в шапке подгоняет масштаб и сдвиг так, чтобы весь граф был виден целиком — полезно после импорта идеи или когда узлов уже много. В правом нижнем углу холста — миникарта (цветные прямоугольники по типу узла, белая рамка — текущая видимая область); клик по ней переносит холст в это место.

`🔦 Фокус` рядом с «Fit all» — переключатель «режима фокуса»: пока он включён и выбран узел, холст подсвечивает только его саму и всё, до чего можно дойти по переходам **вперёд** (обычный обход в ширину по `choices`), а всё остальное (узлы и связи) притушивает. Полезно проследить один путь в разросшемся графе, не отвлекаясь на параллельные ветки; переключение узла или повторный клик по кнопке сразу пересчитывают подсветку.

## 7. Холст: подсветка цели при соединении, заметки-стикеры

При перетаскивании соединения (кружок на правом краю узла, §4) узел под курсором подсвечивается зелёной обводкой в реальном времени — видно, к чему именно ведёт переход, ещё до того, как его отпустишь (сам источник соединения никогда не подсвечивается самому себе). Подсветка использует ту же логику поиска цели, что и фактическое создание перехода при отпускании — то, что подсвечено, и то, что свяжется, никогда не расходятся, в том числе когда под курсором оказалось несколько перекрывающихся узлов (берётся визуально верхний).

**Заметки-стикеры** — авторские пометки прямо на холсте, не часть сюжетного графа: не видны ни «Проверкам», ни боту, ни экспорту связей слоя «Мир» — просто «фломастером по месту», как в Miro. Два способа поставить: кнопка «📝 Заметка» в левой панели (появится по центру текущего вида) или двойной клик по пустому месту холста (появится прямо там). У заметки — свободный текст (печатается прямо в неё), один из 4 цветов (кнопка 🎨 в её мини-панели циклически переключает), перетаскивание мышкой (за фон заметки, не за текст) и удаление кнопкой «✕». Учитываются в «Fit all», но не в миникарте и не в мультивыборе/групповом перетаскивании узлов (см. §11).

## 8. Импорт идей — универсальный JSON-шаблон

Одна идея — самостоятельный кусок сюжета в отдельном JSON-файле: свои узлы (с **локальными** `ref` вместо настоящих id — они одноразовые, только чтобы сослаться друг на друга внутри этого же файла), свои новые переменные, явные **links** — с какими уже существующими узлами (по разделу или тегу) новые узлы должны связаться — и, отдельно, сущности/связи/идеи для слоя «Мир» (§12). Кнопки в левой панели («Импорт идей»): «⬇ Шаблон идеи» скачивает рабочий пример (NPC сам подсказывает донести аккумулятор + пример сущностей/связей DRINK→эффект), «📥 Импорт идеи (JSON)» — открывает файл.

Импорт идёт в два шага — **Анализ → Превью → Слияние**, не сразу: выбор файла считает (не трогая граф) сколько узлов/переменных/сущностей/связей добавится и что из этого уже совпадает с существующим, и показывает окно-подтверждение; граф меняется только по кнопке «Добавить в граф» в этом окне (кнопка «Отмена» просто закрывает превью, ничего не тронув). Числа в превью и то, что реально добавится при подтверждении — гарантированно одни и те же (`analyzeIdea()` и `importIdea()` используют одну и ту же логику сопоставления «новое/уже есть», а не отдельную прикидку на глаз). Превью **интерактивно** — можно переопределить автоматическое сопоставление по каждой сущности бандла и решить, что делать с конфликтующими переменными, прежде чем подтверждать; подробности — §16.

Импорт **только добавляет**: переменные с уже существующим id по умолчанию пропускаются (не перезаписываются, если явно не выбрано «заменить» в превью — §16), узлы никогда не удаляются, а `links` ищутся по **текущему**, уже пополненному списку узлов — поэтому если сегодня ты импортируешь идею про фракции, а завтра другую идею, тоже помеченную тегом `factions`, она сама подключится и к старым узлам, и к тем, что добавила первая идея. Это не «ИИ понимает смысл» — это прямое совпадение по `match_category`/`match_tag`, которые сам указываешь в файле; надёжно и предсказуемо, зато не обещает большего, чем может. Сущности из бандла точно так же не дублируются по умолчанию: авторская сущность (без каталога) считается той же при совпадении вида+имени (без учёта регистра), каталожная — при совпадении вида+ссылки на каталог, если только в превью явно не выбрано другое (§16); типы связей, которых ещё нет в списке, создаются автоматически.

Формат файла:

```jsonc
{
  "idea_id": "npc_self_hint_example",           // просто метка для журнала импортов
  "title": "NPC сам подсказывает, чего не хватает",
  "variables": [                                 // новые мировые переменные (пропускаются, если id уже есть)
    {"id":"v_electricity_home","name":"Электричество в доме","type":"flag","start":0,"min":0,"max":1}
  ],
  "nodes": [
    {
      "ref": "n1",                               // локальная ссылка, только для этого файла
      "title": "NPC: намёк про свет",
      "text": "«Темновато тут. Если бы был аккумулятор — я бы свет наладил.»",
      "type": "background", "category": "ai", "tags": ["energy","story"],
      "trigger": {"kind":"scheduled","afterHours":24,"sinceNode":"","repeat":true},
      "effects": [],
      "sim": {"durationHours":0,"dangerChance":0,"foodCost":0,"waterCost":0,"requiresItems":[],"requiresSkills":[]},
      "ending": "",
      "choices": [
        {"label":"Занести аккумулятор","target_ref":"n2","requires":[],
         "effects":[{"var":"v_electricity_home","op":"set","value":1}],"sim":{"requiresItems":["battery_cell"]}}
      ]
    },
    {"ref":"n2","title":"Свет в доме включён","text":"NPC радуется.",
     "type":"event","category":"energy","tags":["ai"],
     "refs":["e_ivan"],
     "trigger":{"kind":"conditions","all":[]},"effects":[],"sim":{},"ending":"","choices":[]}
  ],
  "links": [
    // от узла n2 — ко ВСЕМ текущим узлам с тегом "energy" (кроме себя), в обе идеи-импорта одинаково
    {"from_ref":"n2","match_tag":"energy","label":"(связано: тоже про энергию)"}
    // или "match_category":"energy" вместо match_tag — тогда сравнивается основной раздел узла, а не доп. теги
  ],

  // "refs" у узла (см. n2 выше) — ссылки на сущности "Мира" по их локальному "ref" внутри этого же
  // бандла (резолвятся в настоящие id так же, как from_ref/to_ref у relations ниже).
  // Необязательно — сущности/связи/идеи для слоя "Мир" (§12), тот же приём с локальным "ref".
  // kind без каталога (character/location/faction/group/concept/resource/effect/animation) —
  // "name" свободным текстом; kind с каталогом (item/skill/action/system) — "refId" реальным
  // id/строкой из Object Plan (PLAN_ITEMS/OS_SKILLS/ACTIONS/SYSTEMS).
  "entities": [
    {"ref":"e_ivan","kind":"character","name":"Иван"},
    {"ref":"e_drink","kind":"action","refId":"DRINK"},
    {"ref":"e_thirstfix","kind":"effect","name":"Восстановление жажды"}
  ],
  "relations": [
    // "type" — свободное имя типа связи: если такого ещё нет в списке типов, он создастся сам
    {"from_ref":"e_ivan","type":"can_perform","to_ref":"e_drink","status":"confirmed","comment":"Иван может пить"},
    {"from_ref":"e_drink","type":"produces","to_ref":"e_thirstfix","status":"confirmed"}
  ],
  "proposals": [
    {"title":"Завести Need-сущность \"Голод\" по аналогии с жаждой","text":"см. design doc"}
  ]
}
```

`target_ref` внутри `choices` ссылается на `ref` из этого же файла (превращается в настоящий id при импорте); можно вместо этого указать `target` с настоящим id уже существующего узла напрямую, если он тебе известен. Узлы новой идеи раскладываются по «слоям» (глубина = кратчайший путь от корня бандла по `target_ref`) слева направо, ниже уже существующего содержимого — так большинство связей идут вперёд, а не петляют, и их несложно донастроить перетаскиванием после импорта.

`links[]` по умолчанию подключается ко **всем** текущим совпадениям (без дублей — одна и та же пара «откуда-куда» не создаётся дважды даже при повторном импорте того же файла) и с потолком в 30 автосвязей на один `link` за один импорт (если тег слишком общий и совпадений больше — остаток можно добрать повторным импортом или сузив тег; в консоль браузера пишется предупреждение). Добавь `"mode":"first"` в `link`, чтобы подключиться только к первому совпадению, а не ко всем. Превью (§16) заранее показывает, сколько автосвязей реально создастся (та же функция сопоставления, что и у настоящего импорта — против «фантомных» узлов бандла, которых физически ещё не существует), и предупреждает, если в самом файле случайно продублировано описание одной и той же связи.

## 9. Хранение и формат

Пишет только `data/story.json`: `{schema_version, variables:[{id,name,type,start,min,max}], nodes:[{id,title,text,type,category,tags,samSystem,arc,chapter,eventSource,actionRef:{action,target},implementationStatus:{logic,characters,object,animation,text},refs,x,y,trigger,effects,sim,choices,ending}], stickyNotes:[{id,x,y,text,color}], entities:[{id,kind,name,ref,note,status,lifecycle}], relationTypes:[{id,name,inverseName,symmetric}], relations:[{id,type,from,to,status,source,comment,conditions,effects}], proposals:[{id,title,text,status,priority,source,createdAt,relatedEntities,relatedSystems,relatedNodes}], worldEvents:[{id,title,actor,action,target,resultLifecycle,effects,comment}], decisions:[{id,title,text,status,source,relatedSystems,relatedEntities,comment,createdAt}]}`, где `sim.requiresItems`/`sim.requiresSkills` — массивы id (а не текст), `entities[].status` — `'active'` или `'deprecated'` (§13, авторский архив), `entities[].lifecycle` — `''`/`planned`/`active`/`dead`/`destroyed`/`removed`/`archived` (§26, судьба сущности ВНУТРИ игрового мира — отдельно от `status`), `relationTypes[].inverseName`/`.symmetric` — необязательные метаданные направления связи (§14), `proposals[].status` — одно из `idea`/`planned`/`accepted`/`implemented`/`rejected`, `.priority` — `low`/`normal`/`high`, `.createdAt` — ISO-дата создания (§15), `worldEvents[].resultLifecycle` — необязательный, чисто справочный итог для `target` (§26, не применяется автоматически), а `decisions[].status` — одно из `defined`/`tentative`/`unknown`/`deprecated`, `.source` — одно из `master-design`/`object-plan`/`story`/`prototype`/`decision` (§28). Файлы, сохранённые до появления любого из этих полей, читаются как раньше — везде подставляются пустые массивы/значения по умолчанию, если поля в файле нет (сущность без своего `status` считается `'active'`, без `lifecycle` — пустым; тип связи без `inverseName`/`symmetric` — обычным однонаправленным; идея без `priority` — `'normal'`; отсутствующие `worldEvents`/`decisions` целиком — пустыми массивами); при первой загрузке (или если файл не содержит своих `relationTypes`) список типов связей заполняется словарём по умолчанию (`member_of`↔`has_member`, `located_at`, `contains`↔`part_of`, `owns`↔`owned_by`, `can_perform`, `uses`, `produces`, `satisfies_need`, `has_skill`, `has_need`, `is_a`, `supports`, `friend_of` и `enemy_of` — оба симметричные) — его можно редактировать и дополнять как обычный список. `Ctrl+Z`/`Ctrl+Shift+Z` — отмена/возврат, общая история правок сразу для ВСЕХ слоёв (§27 — включая `worldEvents`/`decisions`, легко забыть при добавлении нового слоя, как показал попутно найденный баг с `worldEvents`), в браузере, не файла на диске.

Все id (узлов, переменных, сущностей, связей, типов связей) генерируются `uid()` один раз при создании и никогда не зависят от имени/названия — переименование чего угодно никогда не портит ссылки на это, даже те, что лежат в других идея-бандлах или уже сохранённом `story.json` (см. §13, «Стабильные id»).

Шапка показывает, есть ли несохранённые изменения («● Есть несохранённые изменения» / «✓ Сохранено»); `Ctrl+S` сохраняет так же, как кнопка «💾 Сохранить». Попытка закрыть или перезагрузить вкладку с несохранёнными изменениями показывает стандартное предупреждение браузера.

Каждое сохранение сначала читает то, что прямо сейчас лежит в `data/story.json`, и, если там что-то есть, сдвигает роллинг-бэкап (`data/story.backup.01.json` … `.05.json`, см. §23) на один слот и кладёт этот снимок в `01` — только потом пишет новую версию поверх `story.json`. На самом первом сохранении в новой папке бэкапить ещё нечего — файлов не будет, это нормально. Сама запись каждого файла атомарна «бесплатно» — так работает File System Access API (пишет во временный файл, подменяет им целевой только при закрытии потока), поэтому обрыв соединения/скрипта посреди сохранения не может оставить `story.json` наполовину переписанным.

## 12. Режим «Мир»: сущности, связи, идеи-предложения

Второй слой поверх графа сюжета — не сюжетные узлы, а **сущности игрового мира** и типизированные связи между ними, отдельный граф со своими checks, своим импортом и своей правой панелью (общей физически с инспектором узла, но занятой либо тем, либо другим — режимы взаимоисключающие).

**Сущность** (`kind`, `name`/`ref`, `note`) бывает:
- **авторской** — персонаж, локация, фракция, группа, концепт, ресурс, эффект, анимация: имя — свободный текст, ничего не каталогизировано;
- **каталожной** — предмет/навык/действие/система: не дублирует Object Plan, а **ссылается** на него (`ref.refId`) — выпадающий список берётся прямо из уже загруженных `PLAN_ITEMS`/`OS_SKILLS`/`ACTIONS`/`SYSTEMS` (§2); если запись в каталоге переименуют или удалят, «Проверки» это заметят (см. §5).

Левая панель («Сущности», «Идеи / предложения», «Типы связей»): выбор вида + «+ добавить» создаёт сущность (для каталожных видов автоматически берётся первая ещё не занятая запись каталога — поменять можно потом в карточке сущности), поиск фильтрует список (по имени/виду/заметке), список сгруппирован по виду с заголовками-счётчиками. «Идеи / предложения» — вольный текст идеи без структуры («завести систему Х», «а что если Y») со статусом (идея/принято/отклонено); клик по идее в списке предлагает сделать её сущностью выбранного в селекторе слева вида (`promoteProposalToEntity`) — сама идея остаётся в списке с отметкой «принято». «Типы связей» — авторский редактируемый список (как переменные в §1), с несколькими типами по умолчанию (см. §9); связь всегда ссылается на id из этого списка, а не на голую строку — поэтому переименование типа сразу применяется ко всем связям этого типа.

Центральная область — карточка выбранной сущности: поле имени (или выбор из каталога для каталожных видов) + заметка, список её связей — **обеих сторон** сразу (`→` — эта сущность источник, `←` — эта сущность цель), с типом связи и именем другой сущности; клик по имени другой сущности переключает карточку на неё (тот же принцип «клик по ветке — перейти к ней», что и `focusNode()` в §6); «✕» удаляет отдельную связь, «+ добавить связь» создаёт черновую связь от текущей сущности и сразу открывает её в редакторе справа. И ниже — **«Упоминается в сюжете»**: список story-узлов, у которых эта сущность есть во вкладке «Ссылки» инспектора (`node.refs`, §3); клик по узлу переключает на «Сюжет» и сразу выделяет+центрирует его — обратное направление той же Story ↔ World связи, а не отдельная функция. Удаление сущности удаляет и все связи, где она участвует (как удаление узла обрывает переходы на него, §4), но **не** трогает `node.refs` узлов, которые на неё ссылались — те превращаются в дырку, и «Проверки» (§5) это отдельно ловят.

Правая панель в режиме «Мир» — редактор выбранной связи: `от`/`тип`/`к` (все три — выпадающие списки: сущности и типы связей), статус (подтверждено / предположение / устарело), источник (свободный текст — например `idea:bunker_start` или имя design-документа), комментарий, и (тем же общим устройством условий/эффектов, что у узлов и переходов, §3–4) **условия** — когда связь считается действующей — и **эффекты** — что она меняет при срабатывании.

## 13. Режим «только чтение», архивирование сущностей, групповые правки, стабильные id

**Режим «только чтение»** (кнопка «👁 Только чтение» в шапке, оранжевая, когда включена — вместе с оранжевой обводкой всего приложения) блокирует **любую** правку данных в обоих слоях сразу — добавление/удаление/изменение узлов, переходов, переменных, заметок-стикеров, сущностей, связей, типов связей, идей-предложений, а также импорт идей — но не навигацию: клик по узлу/сущности/проблеме в «Проверках», панорама и масштаб холста, разворачивание Dependency Explorer продолжают работать как обычно. Смысл — дать кому-то (или самому себе) спокойно посмотреть граф на общем экране/проекторе без риска случайно что-то сдвинуть или стереть кликом мимо. Три разных способа реакции на попытку правки в этом режиме, выбранные по типу действия:
- Дискретные действия по кнопке (добавить/удалить узел, сущность, связь и т. п.) — тихо ничего не делают; там, где раньше сначала спрашивалось подтверждение (`confirm()`), диалог теперь не появляется вовсе — незачем спрашивать «точно удалить?», если удаление всё равно не произойдёт.
- Перетаскивание (узел, заметка-стикер) — тоже тихо ничего не делает, без единого `alert()`: диалоговое окно на каждый из десятков кадров одного жеста перетаскивания сломало бы весь UX.
- Импорт идеи — единственное действие с явным сообщением об ошибке («Включён режим «только чтение» — импорт отключён»), потому что там и раньше была понятная обработка ошибок с алертом, и импорт — это осознанное, а не случайное действие.

**Архивирование сущностей вместо немедленного удаления** — у каждой сущности мира теперь `status: 'active' | 'deprecated'`. Кнопка «✕»/«🗑 Архивировать» на активной сущности не удаляет её, а помечает устаревшей (обратимо): связи и все `node.refs`, что на неё ссылались, остаются целы, сама сущность просто получает бейдж «(устарело)» в списке и в карточке. У архивной сущности вместо этого — «♻ Восстановить» (возвращает `active`) и «🗑 Удалить навсегда» (настоящее, безвозвратное удаление — то самое старое поведение: каскадно чистит связи, но `node.refs` превращает в дырку, которую ловят «Проверки», §5). Устаревшие сущности не пропадают из уже существующих ссылок и выпадающих списков (иначе `<select>` тихо съехал бы на другое значение) — они только исключены из **новых** подсказок автодополнения (даталист фишек-пикера ссылок, §3) и подписаны «(устарело)», если всё же выбраны как текущее значение `от`/`к` связи.

**Слияние дублей** (`mergeEntities`) — на карточке сущности, если есть другие активные сущности того же вида, появляется пикер «Слить с дубликатом»: перевести все `node.refs` и все `from`/`to` связей с одной сущности на другую (с подтверждением и отчётом, сколько ссылок перенесено), а исходную саму пометить устаревшей — не удалить, слияние всегда обратимо через «♻ Восстановить», если ошиблись адресатом.

**Групповые действия** — когда на холсте/в списке выбрано больше одного узла (`multiSelected.size>1`), правая панель вместо обычных вкладок узла показывает «Групповые действия»: добавить тег всем выбранным узлам разом или задать им один и тот же раздел, плюс групповое удаление (использует тот же `deleteSelectedNodes()`, что и `Delete`/`Backspace`). Действует строго на выбранные узлы — остальной граф не трогается.

**Глобальное переименование тега/раздела** (левая панель, «Переименовать тег/раздел везде в графе») — `renameTagEverywhere(from, to)` переименовывает строку тега/раздела сразу во **всех** узлах графа (не только выбранных), с подтверждением и слиянием тегов, если целевое имя у узла уже есть (не задваивает).

**Стабильные id** — уже было так и раньше, отдельно проверено регрессионным тестом в этом раунде: `uid()` создаёт id по времени создания и случайному хвосту, никогда по имени/названию, поэтому переименование узла, переменной, сущности или типа связи никогда не портит ссылки на них — ни внутри `story.json`, ни в бандле идеи, импортированной раньше.

Сознательно **не реализовано** в рамках этого раунда (см. `11-Story-Map-Backlog.md`, группа W): единый тип «ссылка на сущность» (`{type,id}`), заменяющий собой отдельно `node.refs`, `relation.from/to` и ссылки на переменные в условиях/эффектах — id уже стабильны и непрозрачны, а именно это было настоящей болью в исходном пункте бэклога, так что сам рефакторинг ради унификации формы, а не поведения, посчитан слишком большим риском за небольшую пользу; отдельное поле `alias`/`displayName` в дополнение к `name` — избыточно, `name` и так свободно редактируется; экспорт графа/подграфа в картинку, импорт/экспорт подграфа отдельным файлом и «блокировка/права проекта» для командной работы — прямо отложены самим автором исходного пункта бэклога («если проект станет командным»).

## 14. Dependency/Impact для сущностей мира, метаданные связей, фильтр и Focus Entity

**Dependency Explorer для каталожных сущностей** (предмет/навык/система — те виды, у которых `kind.catalog` заполнен, §12) — их карточка получает секцию **«Используется в сюжете»**, отдельную от обычной «Упоминается в сюжете» (`node.refs`, группа A): это узлы, которые ссылаются на сущность **не явной ссылкой**, а совпадением каталожного значения — предмет через `sim.requiresItems`, навык через `sim.requiresSkills`, система через `category`/`tags` узла (`nodesUsingCatalogEntity()`, `09-world-model.js`). Механизм связи принципиально другой, чем у `node.refs` (совпадение по каталожному id, а не по id сущности «Мира»), поэтому и секция отдельная; у авторских видов (персонаж, локация, фракция…) этой секции нет вовсе — им нечего сопоставлять по каталогу.

**Impact-сводка** — обе секции («Упоминается»/«Используется») теперь показывают рядом с названием узла ту же краткую сводку эффектов, что и список узлов в режиме «Сюжет» (`nodeAffectsSummary()`, §6) — не нужно открывать каждый узел по одному, чтобы увидеть, на какие переменные он влияет. Это сознательно ограниченный, честный Impact View: не «финальное значение, до которого дойдёт сущность», а прямой список фактических эффектов узлов, где она участвует — вычислить первое надёжно нельзя в общем случае (то же самое рассуждение, что и у Dependency Explorer переменных, §1), а второе даёт практическую пользу без ложной точности.

**Метаданные типа связи** (список «Типы связей», §12) — у каждого типа теперь два необязательных поля, редактируемых прямо в списке:
- **Обратное имя** (`inverseName`) — как эта же связь читается со стороны второй сущности: `member_of` → `has_member`. На карточке сущности-цели связь показывается не голым «← member_of», а «→ has_member» — то же самое направление связи, просто сформулированное для той стороны, которая его читает.
- **Симметрична** (`symmetric`) — связь не имеет направления вообще (`friend_of`, `enemy_of`): на обеих карточках показывается одинаково, стрелкой «↔».

Оба поля — централизованные метаданные типа (редактируются один раз в списке типов, применяются сразу везде, где этот тип используется), а не что-то, что дублируется в каждой отдельной связи. Сама связь физически хранится и рендерится как раньше — **одна** запись `{from,type,to}`, читаемая с обеих сторон (§12); показ инверсии/симметрии — вопрос представления, не второй записи.

Также в списке связей на карточке сущности рядом с названием другой сущности — короткий значок «⚙ усл:N, эфф:M», если у связи вообще есть условия/эффекты (пусто, если связь чисто описательная) — чтобы видеть с одного взгляда, какие связи механически участвуют в игре, а какие просто фиксируют факт.

**Фильтр по типу связи** — выпадающий список над списком сущностей («Все типы связей» / конкретный тип) сужает список до тех, у кого есть хотя бы одна связь (в любом направлении) выбранного типа.

**Focus Entity** (кнопка «🔦 Фокус» + глубина 1/2/3/«Все», рядом с фильтром) — сужает список сущностей до кластера в N связях от выбранной, **без учёта направления** (в отличие от режима фокуса в «Сюжете», §6, где направление и есть весь смысл — там прослеживается ветка вперёд по `choices`; здесь важна сама связность, а не её направление). Поскольку у режима «Мир» сознательно нет пространственного холста (карточка + список, §12), «фокус» реализован как сужение видимого списка, а не как притушивание на канве — тот же практический эффект («не отвлекаться на остальной граф»), доступным здесь инструментом.

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа J): **авто-создание второй, зеркальной записи связи** при указании `inverseName` — намеренно не делается, чтобы не заводить два физических объекта, которые могут разойтись (например, условия/эффекты поправили у одной записи, а у её «зеркала» — забыли); инверсия — только чтение существующей связи с другой стороны, не вторая мутируемая копия. **Проверка/защита от «некорректного направления»** связи (например типа `located_at` от Фракции к Персонажу, если смысл предполагает обратное) — потребовала бы отдельно объявлять для каждого типа связи допустимые виды сущностей на `от`/`к` (ещё один конфигурируемый список на весь тип, который в реальности почти никто не будет заполнять) ради предупреждения, которое и так видно человеку по названию связи и именам сущностей — цена конфигурации показалась выше пользы.

## 15. Идеи/предложения как полноценный backlog

До этого раунда идея-предложение было строкой в списке без собственной карточки: клик по ней сразу спрашивал «сделать сущностью?» — не было способа просто открыть идею, поправить текст или посмотреть, что с ней связано. Теперь у идеи — **своя карточка**, тот же физический блок `#entityDetail`, что и у сущности, занятый одним из двух взаимоисключающе (`selectedProposalId`/`selectedEntityId` — выбор одного снимает выбор другого, как и `selectedRelationId` в §12). Клик по строке идеи в списке слева **только открывает карточку** — никаких диалогов на голом клике.

**Поля идеи**: заголовок и текст (как раньше), плюс:
- **Статус** — теперь пять состояний вместо трёх: идея → запланировано → принято → **реализовано** → (или) отклонено. «Реализовано» проставляется автоматически при промоушене в сущность/узел (см. ниже), но можно выставить и вручную, если идея воплотилась не через сам инструмент (например, руками в коде игры).
- **Приоритет** (низкий/обычный/высокий) — высокий отмечен значком 🔺 прямо в списке слева, чтобы не открывать каждую карточку.
- **Источник** (свободный текст — `playtest#3`, `design.md`, как у `relation.source` в §12) и **дата создания** (проставляется автоматически, только для чтения).

**Проposal → Object Plan** — карточка получила пикер «Связанные системы» (те же чипы, что у раздела/тегов узла, §3, источник — `SYSTEMS` из Object Plan): отметить, каких игровых систем идея касается, не создавая пока ничего реального.

**Proposal → сущность / Proposal → узел сюжета** — два способа «построить» идею, оба доступны прямо из карточки:
- **«→ Сущностью»** (было и раньше, теперь явной кнопкой с выбором вида, а не диалогом на клике) — создаёт сущность в «Мире» по названию/тексту идеи и переходит к ней.
- **«→ Черновой узел сюжета»** (новое) — создаёт обычный узел в «Сюжете» (заголовок и текст — из идеи, раздел — из первой связанной системы, если она указана), переключается на «Сюжет» и сразу выделяет его — дальше это ничем не отличающийся от любого другого узел.

Оба действия помечают идею статусом `implemented` (не `accepted` — «принято» и «сделано» теперь разные состояния) и запоминают, во что она превратилась (`relatedEntities`/`relatedNodes`), чтобы не терять эту нить. Идею можно и **вручную привязать** к уже существующему узлу сюжета (пикер «привязать существующий» в карточке) — не каждая идея должна порождать новый черновик, если подходящий узел уже есть; отвязка снимает только упоминание, сам узел не трогает.

**Связанные сущности** — тот же чип-пикер, что и у `node.refs` (§3), с тем же кликом-переходом по названию чипа (переключает на сущность в «Мире», закрывая карточку идеи).

**Целостность ссылок** — идея, как и всё остальное в этом слое, не должна безмолвно указывать в никуда: удаление сущности (`deleteEntity`) вычищает её из `relatedEntities` любых идей, что на неё ссылались; удаление узла (`deleteNode`) — аналогично из `relatedNodes`; слияние дублей (`mergeEntities`, §13) переносит ссылку идеи на целевую сущность вместе с `node.refs`/связями, а не оставляет её висеть на устаревшей.

## 16. Интерактивное превью импорта: reuse/create/skip, конфликты переменных, проекция автосвязей

До этого раунда превью импорта (§8) было только сводкой цифр — узнать, что сопоставилось автоматически с чем именно, и повлиять на это, было нельзя: авторская сущность бандла либо молча сливалась с существующей по имени, либо молча заводилась новой, и лишний символ в имени («Иван » вместо «Иван») тихо создавал дубль вместо ожидаемого слияния. Теперь превью — рабочий инструмент, а не просто индикатор.

**Сущности бандла** — под сводкой (если у бандла вообще есть `entities`) список каждой сущности с её собственным выпадающим списком:
- «Использовать существующую: `<имя>`» — только если автоматическое сопоставление (то же правило, что и раньше: вид+имя без учёта регистра, или вид+`refId` для каталожных) вообще что-то нашло; выбрано по умолчанию, когда нашло.
- «Создать новую» — принудительно завести новую сущность, даже если что-то совпало (по умолчанию, если совпадений не было).
- «Пропустить (не создавать)» — не создавать сущность вообще; всё, что на неё ссылалось через `ref` внутри этого же бандла (`node.refs`, `relations[].from_ref/to_ref`), не резолвится и естественно отваливается — так же, как если бы ссылка вела на уже удалённый id (никакого отдельного механизма для этого не понадобилось).

Список строится и пересчитывается той же функцией, что считает и итоговую сводку (`analyzeIdea(data, overrides)`), поэтому смена выбора у одной сущности сразу отражается в счётчиках «новых/совпало» выше — это те же самые данные, а не два независимых представления, которые могут разойтись.

**Конфликты переменных** — раньше переменная с уже существующим id просто пропускалась молча, даже если её параметры (название, тип, диапазон) в бандле отличаются от того, что уже в графе — расхождение было не видно вообще. Теперь такие переменные (id совпадает, но `name`/`type`/`start`/`min`/`max` отличаются) отдельно перечислены в превью с выбором: «Оставить как в графе» (по умолчанию, старое поведение) или «Заменить параметрами из идеи» (осознанная перезапись на месте — id и все ссылки на переменную остаются рабочими, меняется только её определение).

**Проекция автосвязей** (`applyAutoLinks()`) — общая функция для реального создания автосвязей и для их подсчёта в превью, вынесенная из `importIdea()`: работает по любому списку «node-подобных» объектов (`{id, category, tags, choices}`), поэтому превью может прогнать её по «фантомным» узлам бандла (у которых есть `category`/`tags`, но ещё нет настоящего id и они не лежат в графе) точно так же, как реальный импорт прогоняет её по-настоящему созданным узлам. Счётчик «уже назначенных целей» на источник хранится отдельно от самого факта записи в `choices` — иначе в режиме подсчёта (без реальной записи) второй `link` с тем же источником не видел бы, что первый уже «занял» часть целей, и посчитал бы лишнее.

**Повторяющиеся описания связи** — если в самом файле идеи два `link`-описания с одинаковыми `from_ref`/`from`+`match_category`+`match_tag`+`mode` (обычно copy-paste в JSON), превью считает и показывает предупреждение; на сам результат это не влияет (дубли-переходы и так не создаются — см. выше), это просто сигнал автору файла, что стоит проверить JSON.

Формат вызова для тех, кто трогает эти функции из кода/тестов: `analyzeIdea(data, overrides)` и `importIdea(data, overrides)`, где `overrides` необязателен (`importIdea(data)` без второго аргумента ведёт себя как раньше) и имеет вид `{entities:{[ref]:'match'|'new'|'skip'}, variables:{[id]:'keep'|'replace'}}`.

**Несколько файлов за один выбор** — `#ideaFileInput` принимает `multiple`; выбранные файлы читаются и парсятся сразу все, но дальше идут в очередь (`ideaImportQueue`) и проходят Анализ/Превью/Слияние КАЖДЫЙ ПО ОТДЕЛЬНОСТИ, один за другим (заголовок модалки показывает «(2 из 5)» и т. п., когда файлов больше одного) — не единый комбинированный бандл. Это не костыль, а прямое следствие того, что `analyzeIdea`/`importIdea` уже устроены как «дедупликация по ТЕКУЩЕМУ состоянию графа»: после слияния файла №1 файл №2 увидит на графе уже добавленное файлом №1 и корректно сопоставит совпадения — если бы вместо этого все N файлов сначала слились в один бандл в памяти и только потом прогонялись через `analyzeIdea` один раз, совпадения МЕЖДУ файлами пачки не сматчились бы (каждый бандл при анализе видит только текущий граф, а не соседние ещё не слитые бандлы). «Отмена» на одном файле пачки пропускает только его и переходит к следующему, не отменяя всю пачку. Итоговый алерт с суммой по всем файлам показывается один раз в конце пачки (а не по одному на файл — это просто утомляет), только когда файлов больше одного; для одного файла всё выглядит и ведёт себя ровно как раньше. Файл, который вообще не читается как JSON или не проходит базовую проверку (`nodes` — массив), не блокирует остальную пачку — ошибка чтения собирается в отдельный алерт со списком проблемных имён файлов, а годные файлы всё равно встают в очередь.

## 17. Шаблоны сцен, Арка/Глава, режим «Таймлайн»

**Шаблоны сцен** (левая панель, «🧩 Вставить шаблон») — небольшая встроенная библиотека готовых структурных паттернов (`STORY_TEMPLATES`): **Столкновение** (событие → успех/неудача), **Развилка** (один выбор с тремя путями), **Находка** (фоновое обнаружение → одно продолжение), **Бой** (победа/поражение/бегство). Вставка создаёт сразу несколько связанных узлов от текущей точки спауна (там же, где появился бы узел от кнопки «+ Событие», §3) — тот же приём раскладки по «слоям», что и у идеи-импорта (`layoutIdeaEntries`, §8), поэтому исходы сразу выстраиваются по колонкам, а не грудой друг на друге. Шаблон — **чистая структура**: только узлы/переходы, без переменных, сущностей и автосвязей — этим он проще и легче полноценного импорта идеи (§8/§16), которые остаются инструментом для содержательных, а не структурных, кусков сюжета. Корневой узел шаблона сразу становится выбранным.

**Арка / Глава** (`node.arc`/`node.chapter`, вкладка «Основное» в инспекторе, §3) — необязательная, чисто навигационная группировка узлов свободным текстом (с автодополнением по уже использованным в графе значениям), не меняющая ни модель узла, ни сам граф, и не видная боту-симулятору. Левая панель получила два фильтра — «Арка: все»/«Глава: все» — списки вариантов собираются из того, что реально уже встречается на узлах графа и пересобираются при каждой правке (как и фильтр по типу связи в «Мире», §14); поиск по узлам (§6) тоже проверяет текст арки/главы. «Арка» — более крупная группировка (например, «Арка бункера»), «Глава» — более мелкая (например, «Глава 2: Вылазка») — оба поля равноправны, между ними нет проверяемой иерархии (глава не обязана «принадлежать» конкретной арке формально).

**Режим «Таймлайн»** (третья кнопка в шапке, «🕐 Таймлайн») — не отдельный граф (в отличие от «Мира», §12), а альтернативное представление узлов «Сюжета»: только те, у кого есть **определённый момент в игровом времени** — это узлы «▶ Старт» (час 0) и «⏱ Фоновое, по таймеру» (час считается по цепочке `afterHours`/`sinceNode`: свой `afterHours` плюс расчётный час узла, от которого идёт отсчёт, а если `sinceNode` пусто — то от старта игры, то есть от 0). Узлы «⚑ По условиям» **не имеют** определённого момента вообще — их время зависит от игрока, а не от часов — поэтому они честно показаны отдельным списком «Вне хронологии», а не потеряны молча и не придуманы задним числом (та же честность, что и у Runtime Availability, §5, — не пытаться посчитать то, что в принципе не вычисляется). Туда же попадает фоновый узел, чья цепочка `sinceNode` сломана: ссылается на несуществующий узел, зациклена (A ждёт B, B ждёт A — поймано защитой от цикла), или в итоге упирается в условный узел вместо старта.

Хронология — горизонтальная лента карточек слева направо в порядке расчётного часа (не пропорционально масштабированная временная шкала — просто честный порядок с подписанным часом на каждой карточке, без ложной точности о том, где именно на прямой между двумя точками легла бы такая-то карточка). Клик по карточке (в хронологии или вне неё) переключает на «Сюжет» и сразу выделяет+центрирует узел — тот же принцип «клик — переход», что и везде в инструменте. У режима нет своей левой панели (при переходе в «Таймлайн» скрываются и `storyLeftPanels`, и `worldLeftPanels`) и своего масштаба/панорамы — это простой список, а не второй пространственный холст, тем же намеренным упрощением, что и у карточки сущности в «Мире» (§12).

## 18. Симуляция: лёгкий inline-прогон логики («▶ Играть»)

Кнопка «▶ Играть» в шапке (доступна в любом режиме и даже в «только чтение» — сама симуляция ничего не пишет в `nodes`/`variables`, это чтение/просмотр, а не правка, как и клик по узлу или Dependency Explorer) открывает модальное окно: пошаговый прогон графа с начала, «на живую», без выхода из Story Map. Это **не** замена `story-bot/` (`10-Story-Bot.md`) — полноценному боту-симулятору с собственным движком — а быстрая проверка «эта логика вообще работает так, как я задумал?» прямо во время редактирования, без переключения в другой инструмент.

**Как это работает:**
- Старт — от единственного узла «▶ Старт» (если его нет, «Проверки» уже должны на это указать, §5); применяются его собственные эффекты, к счётчику часов прибавляется его `sim.durationHours`.
- Показаны переходы **текущего** узла — доступные (прошли свои `requires`) кликабельны, недоступные показаны серым с подсказкой при наведении, какое условие не выполнено (то же самое «честно показать, чего не хватает», что и у самих условий в инспекторе, а не просто спрятать недоступный вариант).
- Клик по переходу применяет его эффекты, затем эффекты узла, в который он ведёт, и обновляет счётчик часов.
- Значения переменных клэмпаются к их `min`/`max` при каждом применении эффекта — так же, как подразумевает диапазон переменной везде в инструменте (§1, §5).
- **Фоновые узлы тикают параллельно**, тем же расчётом часа, что и в «Таймлайне» (`resolveScheduledHour`, §17) — если расчётный час фонового узла наступил (текущие часы ≥ его часа), его эффекты применяются автоматически, попадая в журнал отдельной строкой, независимо от того, каким путём идёт игрок. Повторяющийся (`repeat`) фоновый узел планирует свой следующий момент на `+afterHours` от текущего и может сработать снова позже в том же прогоне.
- Узел с заполненной **концовкой** останавливает прогон и показывает её метку. Узел без переходов и без концовки — тупик, тоже останавливает прогон (с пояснением, а не тихим зависанием). Лимit в 200 шагов на всякий случай останавливает прогон, если граф зациклен без выхода к концовке — тоже с явным сообщением, а не бесконечным «зависанием» интерфейса.
- «🔁 Заново» сбрасывает прогон к начальному состоянию (заново от старта, переменные — на свои `start`); «Закрыть» прячет окно и отпускает состояние прогона.

Сознательно **не смоделировано** (см. `11-Story-Map-Backlog.md`, группа N): автономная активация узлов «⚑ По условиям» вне явных переходов графа. У фоновых узлов есть однозначный механизм («тикают по часам», уже описанный в §17/§3), а вот может ли условный узел стать «текущим» сам по себе, без клика по ведущему к нему переходу — неоднозначный, ещё не описанный в документе вопрос: моделирование этого потребовало бы решить, что происходит при конкуренции нескольких одновременно готовых условных узлов, как это соотносится с уже идущим прогоном и т. д. — рисковать неверной, придуманной догадкой хуже, чем оставить это честно за скобками лёгкого прогона. Полноценный `story-bot/` — то место, где это в итоге должно решаться по-настоящему.

## 19. Визуализация тупиков и источник события

**Визуализация тупика прямо на графе** — раньше «нет переходов и нет концовки» было видно только текстовой строкой в «Проверках» (§5); теперь такой узел получает значок «⛔» рядом с названием — и на карточке холста, и в списке слева, — а не только в отдельной панели, которую ещё нужно было прокрутить и прочитать. Узел с заполненной **концовкой** никогда не получает этот значок, даже если у него тоже нет переходов — «тупик + концовка» это нормальный конец истории, а не забытая ветка. Сама проверка (§5) заодно повышена с уровня `info` до `warn` — «нет переходов, нет концовки» почти всегда означает, что ветку забыли доделать, а не намеренный дизайн, в отличие от «полностью изолирован» (нет вообще ничего — ни входящих, ни исходящих, ни концовки), который остался на уровне `info`, потому что это куда более вероятный черновик-задел на будущее, а не забытая уже написанная ветка.

**Источник события** (`node.eventSource`) — необязательная авторская пометка вида «кто/что это инициирует»: Игрок / NPC / Фракция / Мир (окружение) / Локация / Таймер / Игровая система (`EVENT_SOURCES`, `01-core-utils.js`). Показана значком в списке узлов и на карточке холста (в строке рядом с «когда доступен»), участвует в поиске по узлам (§6). Сознательно **не объединена** с существующим `trigger.kind` (старт/по условиям/по таймеру) в один общий «Entry Point»-enum (Game Start/World Event/Faction Event/NPC Event/Scheduled Event из исходного пункта бэклога) — это дало бы две классификации одного узла, которые пришлось бы поддерживать синхронно и которые всё равно способны разойтись; вместо этого `trigger.kind` отвечает за МЕХАНИКУ («как это срабатывает» — единственное, на что реально смотрят «Проверки» и симуляция, §18), а `eventSource` — за смысл («кто за этим стоит», чисто авторская пометка для навигации по разрастающемуся автономному миру). Комбинация обоих полей и так даёт все перечисленные в бэклоге сочетания (например, «по условиям» + «Фракция» читается как «событие фракции») без второго закрытого списка.

## 20. Обозреватель триггеров и цепочка последствий

**Обозреватель триггеров** («🔔 Триггеры» в шапке) — снимок-на-открытие (как окна импорта/симуляции — не подписан на `renderAll()`, обновляется заново при каждом открытии и на ввод в своём поиске): все узлы графа, кроме стартового, одним экраном — условие или расписание срабатывания (`nodeTriggerSummary()`: список условий через «И» для «⚑ по условиям», часы + от какого узла + отметка повтора для «⏱ по таймеру»), источник события (§19) и сводка «→ на что влияет» (`nodeAffectsSummary`, та же, что и в списке узлов, §6) — вместо того чтобы открывать каждый узел по одному ради тех же трёх фактов. Собственное текстовое поле фильтрует по названию, тексту условия и источнику; клик по строке закрывает окно и переключает на неё в «Сюжете» (`focusNode`) — тот же принцип «клик — переход», что и везде в инструменте.

**Возможная цепочка последствий** — кнопка «🔗» у перехода (вкладка «Переходы» в инспекторе) разворачивает под ним, куда дальше могут докатиться эффекты этого выбора: переменная, которую он меняет → какие ещё узлы (или связи «Мира», §12) её читают → их СОБСТВЕННЫЕ эффекты → какие переменные это затрагивает дальше → и так далее, до 3 шагов или 30 записей (что наступит раньше — защита от взрыва на плотном графе). Использует ту же функцию поиска «кто читает/пишет переменную», что и Dependency Explorer (`variableDependents()`, §1) — просто раскрученную на несколько шагов подряд вместо одного. Каждая строка кликабельна — переходит к узлу-читателю.

Это **не предсказание** «вот что произойдёт», а карта возможного влияния — честно подписано в самой панели («не гарантия — зависит от значений переменных в момент выбора»). Узнать НАВЕРНЯКА, станет ли условие следующего узла истинным именно из-за этого выбора, нельзя без знания фактических значений всех переменных на тот момент — то же самое рассуждение, по которому «эффект делает более позднюю ветку недостижимой» сознательно не реализовано как жёсткая проверка (группа G, §5): цепочка показывает связи («это ЗАВИСИТ от того же»), а не исходы («это ТОЧНО случится»). Связи `relations` (слой «Мир») попадают в цепочку как конечная точка (их эффекты не раскручиваются дальше) — два разных графа сюжета и мира сознательно не смешиваются в один сквозной обход без явного повода.

## 21. Источники событий (расширено), эффекты на ресурсы, «Действие → Цель»

**Источник события — расширен** (`EVENT_SOURCES`, §19): добавлены «Нехватка ресурса», «Погода», «Отношения (NPC/фракции)», «Случайное событие» — только добавлены, ничего не переименовано и не удалено, старые узлы с уже выбранным «Мир (окружение)»/«Таймер»/«Игровая система» не остались без подписи.

**Эффекты на ресурсы** (вкладка «Симулятор», `sim.resourceEffects`) — то же самое, что `sim.foodCost`/`sim.waterCost` (которые остались как есть — уже используются, ломать незачем), только для **любого** ресурса Object Plan, а не только еды и воды. Список типов ресурса **не хардкожен** — Object Plan не хранит отдельный каталог ресурсов вообще (вода/энергия/топливо/лом — это просто `os.resourceType` на предметах-контейнерах/баках в `PLAN_ITEMS`, безо всякого единого перечня где-либо), поэтому Story Map сам вычисляет список из уже загруженного `PLAN_ITEMS` (`getResourceTypes()`, `09-world-model.js`) — заведут в Object Plan новый тип ресурса, он тут же станет доступен и здесь, без правки Story Map. Известные типы (`water`/`energy`/`fuel`/`scrap`) подписаны по-русски, незнакомый будущий тип показывается как есть (сырой строкой) — честнее, чем молчать о нём.

**«Действие → Цель»** (`node.actionRef`, вкладка «Ссылки») — структурная связка «что делает игрок → над чем», отдельная от общего списка ссылок на сущности мира (`node.refs`, группа A) выше на той же вкладке: там просто набор упомянутых сущностей без ролей, здесь — ровно два явных поля, «Действие» (обязательно сущность вида «Действие (Object Plan)», §12 — то есть один из `ACTIONS`: `TAKE`/`DROP`/`OPEN`/`EAT`/… ) и «Цель» (любая сущность мира). Совпадает по смыслу с конвенцией `perform_action(action_id, target)` из мастер design-документа игры — то есть уже готовая, структурированная пара для будущего кодогенератора/бота, а не два неразличимых значения в общем списке ссылок, где непонятно, какое из них действие, а какое — над чем оно выполняется. Пока оба поля не выбраны — секция ничего не добавляет к графу; когда выбраны — под селектами появляется простая читаемая сводка «Действие → Цель». Проверки (§5) ловят ссылку на сущность, которую с тех пор удалили — тем же способом, что и у `node.refs`.

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа Q): общий структурный слой Requirements (item+quantity+skill+state+location+time+tool) поверх уже существующих условий (`requires` на мировые переменные) и `sim.requiresItems`/`requiresSkills` — при ближайшем рассмотрении такого общего слоя нигде в репозитории **не существует** (несмотря на формулировку исходного пункта бэклога, будто он уже есть) — ближайшая по духу вещь, `OS_ACTION_FIELDS` в Object Plan, это конфигурация конкретного действия на конкретном предмете (инструмент/расход/время/навык), а не переиспользуемая структура условия где угодно, и в ней тоже нет ни локации, ни времени суток. Построить полноценный собственный вариант означало бы либо ломать уже рабочий и покрытый тестами формат `sim.requiresItems` (сейчас — плоский массив id, quantity потребовал бы менять его на массив объектов), либо изобретать с нуля два совершенно новых механизма, которых в инструменте пока нет вообще ни в каком виде — отслеживание локации игрока и время суток. Слишком большой и рискованный кусок для одного захода — честнее было отложить, чем сделать наполовину.

## 22. Story ↔ Object Plan: готовность узла, статус предмета, Orphan Detection

**Готовность узла к реализации** (`node.implementationStatus`, вкладка «Основное») — чисто продакшен-трекинг, отдельный от Object Plan-а: там статус — про конкретный ПРЕДМЕТ каталога (готов ли ассет), здесь — про конкретный УЗЕЛ сюжета сразу по пяти аспектам: Логика, Персонажи, Объекты/предметы, Анимации, Текст/диалоги. У каждого аспекта — своё состояние (не начато/в работе/готово — тот же словарь, что использует и Object Plan для своих предметов, чтобы не плодить третий вариант той же идеи). Сводка «N/5» (с «✅», когда все пять готовы) видна и в списке узлов слева, и прямо на карточке холста — не открывая каждый узел по одному, чтобы понять, сколько уже реально сделано. Чисто метаданные: не влияют ни на граф, ни на «Проверки», ни на симуляцию (§18).

**Статус реализации из Object Plan** — Object Plan уже сам ведёт статус готовности каждого предмета (`todo`/`wip`/`done`/`skip`, вручную или автоматически по шагам готовности — `object-plan/js/07-store.js`) и сохраняет его в `data/object_plan.json` того же проекта. Вместо того чтобы заводить второй, параллельный статус, Story Map **читает** этот файл (только на чтение, тем же best-effort способом, что и остальные попытки чтения проекта — молча ничего не показывает, если файл не найден или папка не подключена) и показывает его на карточке сущности вида «Предмет (Object Plan)»: секция «Данные из Object Plan» — игровые системы предмета (`PLAN_ITEMS[].sys`, переведённые в названия систем) и его статус, если он выставлен вручную. Читается **только ручной** статус (`store.status[id]` в терминах Object Plan) — автоматический расчёт по шагам готовности (картинка/размеры/анимации и т. п.) зависит от `data/objects`, которую Story Map иначе никогда не парсит; честнее показать «не отмечено вручную», чем воспроизводить чужую эвристику неточно.

Вместе эти две вещи и есть трассировка **Story → World Entity → Object Plan → Game System** из исходного пункта бэклога: узел ссылается на сущность (`node.refs`/`actionRef`/`sim.requiresItems`, §3/§21) → сущность каталожно привязана к предмету Object Plan (§12) → карточка сущности показывает его игровые системы и статус реализации (это добавление). Обратная трассировка «кто использует `water_tank`» уже была отдельно реализована в группе H/O: секция «Используется в сюжете» на карточке любой каталожной сущности (`nodesUsingCatalogEntity()`, §14).

**Orphan Detection** — новая проверка (info-уровень, как «изолирован» у узлов, §5): сущность мира, на которую вообще ничто не смотрит — ни `node.refs`, ни `node.actionRef`, ни связь, ни идея-предложение — считается потенциально забытой. Не warn: это может быть и забытым мусором, и осознанным заделом на будущее (сущность создали заранее, ещё не успели использовать) — та же логика, что и у остальных info-уровня проверок в инструменте. Уже архивированные (`status:'deprecated'`) сущности не проверяются отдельно — для них уже есть свой сигнал (бейдж «устарело»). Orphan Detection для **переменных** и **узлов** уже была раньше (соответственно «переменная нигде не используется» и «нет входящих переходов»/«изолирован», §5) — тут только добавлена недостающая часть для сущностей «Мира».

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа R): Orphan Detection для самих объектов Object Plan (предметы каталога, которые ничем в Story Map не используются) — каталог Object Plan заведомо намного шире, чем то, что упомянет один конкретный сюжет: пометить «неиспользуемым» большинство каталога для каждого отдельного проекта означало бы утопить редкий настоящий сигнал в шуме, а не дать полезное предупреждение.

## 23. Обзор проекта, версия формата, надёжность файла

**Обзор проекта** («📊 Обзор» в шапке, `16-project-overview.js`) — модалка-снимок (не подписана на `renderAll()`, как «Триггеры»/«Играть») со сводной статистикой по всем слоям сразу: узлы (всего и по типам), переменные, сущности мира (всего и по видам), связи, идеи-предложения (всего и по статусам), агрегированная готовность к реализации (сумма `done`/`total` по всем узлам сразу, §22), число ошибок/предупреждений/инфо из «Проверок» (§5), версия формата файла и время последнего сохранения. Не отдельная страница со своей навигацией — тот же принцип, что и у остальных «одним экраном» модалок инструмента (Триггеры §20, Симуляция §18): не плодить второй способ переключаться между видами ради панели, которая только показывает цифры. Кнопка «⬇ Диагностический отчёт» скачивает те же цифры плюс полный список проблем из «Проверок» одним JSON-файлом — для вставки в баг-репорт или обсуждение, без ручного копирования по кусочкам.

**Версия формата** (`schema_version` в `data/story.json`, `STORY_SCHEMA_VERSION` в коде) — до сих пор каждое изменение формата было additive (новое поле — с `||`-фоллбэком на чтении и явным бэкфиллом в `loadStoryFromProject`, как `actionRef`/`implementationStatus` в группах Q/R), поэтому и версия всё ещё `1`. Заготовка на будущее (`STORY_SCHEMA_MIGRATIONS`/`migrateStoryData()`) заведена заранее, а не в момент, когда впервые понадобится по-настоящему несовместимая смена формата — тогда цена ошибки уже «тихо неверно прочитанный старый файл», а не лишняя пустая заготовка в коде.

**Надёжность файла** — раньше был один бэкап-слот (`data/story.backup.json`, обновлялся при каждом сохранении). Теперь это роллинг-история из пяти снимков (`data/story.backup.01.json` — самый свежий, … `.05.json` — самый старый, `rotateStoryBackups()`): при новом сохранении текущий `01` сдвигается в `02`, тот — в `03` и так далее, самый старый (`05`) теряется. Срабатывает в двух местах: перед обычным сохранением (бэкапится то, что СЕЙЧАС на диске — т. е. состояние ДО этого сохранения) и перед слиянием импортированной идеи (`backupCurrentStateBeforeImport()`, §16) — бэкапится то, что СЕЙЧАС в памяти, т. е. состояние ДО слияния. Второе не сводится к первому: сам импорт на диск ничего не пишет, поэтому без отдельного вызова «до импорта» на диске было бы неотличимо от «после последнего обычного сохранения», если между ними были ещё не сохранённые правки.

Отдельно — восстановление при повреждённом файле (`readStoryJsonWithRecovery()`): если `data/story.json` существует, но не читается как JSON (битый файл, обрыв записи внешним инструментом и т. п.), загрузка не начинает молча с пустого графа, а перебирает бэкапы от самого свежего (`01`…`05`, затем — на всякий случай — старый однослотовый `story.backup.json`, если папка ещё не пережила ни одного сохранения в новом формате) и подставляет первый, который читается как валидный `story.json`, с явным предупреждением, из какого именно слота восстановлено. Если не читается вообще ничего (и сам файл, и все бэкапы повреждены или отсутствуют) — тоже явное предупреждение, а не тихая пустота: автоматика дальше бессильна, дело за ручной проверкой `data/`. Файл, которого попросту ещё не существует (самый первый запуск в новой папке) — это НЕ повреждение и предупреждения не вызывает: `readStoryJsonWithRecovery` различает «файла нет» и «файл есть, но битый» именно для этого.

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа S): отдельная валидация JSON перед сохранением — `collectStoryJSON()` строит объект напрямую из состояния в памяти, а не парсит текст, так что «сохранить нечитаемый JSON» структурно невозможно (кроме уже отловленного `try/catch` вокруг `JSON.stringify`); реальный риск порчи — со стороны ЧТЕНИЯ (внешнее редактирование, обрыв на другом инструменте), а не записи, и именно на это отвечает восстановление из бэкапа выше. Отдельная стартовая страница Project Overview вместо модалки — намеренно не заводилась: инструмент не имеет своей навигации/роутинга ни для чего другого, ещё одна отдельная «страница» усложнила бы это исключение ради панели с цифрами.

## 24. Командная палитра, keyboard-first, контекстное меню, инлайн-правка

**Keyboard-first** — к уже существовавшим Ctrl+S/Ctrl+Z/Ctrl+Shift+Z/Ctrl+A/C/V/Delete добавлены: `N` — добавить событие (то же самое, что кнопка «+ Событие»), `F` — Fit all, `Tab` (при выбранном ровно одном узле) — быстрый связанный дочерний узел (см. ниже), `Escape` — закрыть любую открытую модалку/контекстное меню, а если ничего не открыто — снять выделение узла (`closeTopModal()` в `11-init.js` проверяет по очереди все известные модалки и закрывает первую открытую). Как и раньше, буквенные клавиши не перехватываются, пока фокус в поле ввода/textarea/select — иначе набор текста в названии узла превратился бы в минное поле из горячих клавиш; `Escape` и `Ctrl+K`/`Ctrl+S` — исключение, они разбираются РАНЬШЕ этой проверки и работают всегда (первые два — чтобы можно было выйти из поля вообще без мыши, `Ctrl+S` было так же и раньше).

**Командная палитра** («⌘ Команды» / `Ctrl+K`, `17-command-palette.js`) — один текстовый поиск по всем разбросанным по шапке действиям (добавить узел/заметку, сохранить, подключить папку, переключить «только чтение», играть, открыть Триггеры/Обзор, Fit all/сброс масштаба/фокус-режим, переключить режим Сюжет/Мир/Таймлайн) сразу с переходом к любому узлу по названию или тексту — набранный запрос ищет и там, и там одновременно, смешивая результаты в один список (совпадения по узлам показываются только когда есть непустой запрос, иначе список из сотен узлов захлестнул бы статичные действия). Стрелки перемещают выделение по списку, Enter выполняет выделенный пункт, клик — тот же эффект. Тот же принцип "снимок-на-открытие", что и у Триггеров/Обзора — палитра не подписана на `renderAll()`, пересчитывается заново при каждом открытии и на каждый ввод.

**Контекстное меню** (правый клик на узле/переходе, добавлено в `03-canvas.js`) — те же действия, что уже доступны кнопками/горячими клавишами, просто под рукой в точке клика, без похода к панели слева/инспектору:
- на узле: ✏️ Переименовать (запускает инлайн-правку, см. ниже), ➕ Дочерний узел, ⚡ Добавить эффект, 📋 Дублировать, 🔦 Фокус отсюда, 🗑 Удалить узел;
- на переходе (связи между узлами): 🗑 Удалить переход.

Переходы на холсте рисуются тонкой линией (2px) — для правого клика этого недостаточно, поэтому под каждой видимой линией лежит невидимая широкая копия (`.edge-hit`, 14px, `stroke:transparent`) с теми же `data-fromnode`/`data-choice` — она и ловит клик, `#edgeLayer` в остальном остаётся `pointer-events:none` (иначе пустое место между линиями мешало бы панораме/рамке выделения). Меню закрывается кликом мимо себя, скроллом холста или `Escape` (последнее — через тот же общий обработчик, что закрывает модалки).

**Быстрые составные действия** (`02-graph-state.js`) — раньше требовавшие нескольких отдельных шагов действия, теперь одним:
- **Add Child** (`addChildNode()`, клавиша `Tab` или пункт меню «➕ Дочерний узел») — создаёт новый узел справа от исходного И СРАЗУ добавляет переход к нему от исходного узла, одним шагом истории (раньше — «+ Событие», затем вручную протянуть связь курсором);
- **Add Consequence** (`addConsequenceToNode()`, пункт меню «⚡ Добавить эффект») — добавляет пустую строку эффекта на узел и сразу переключает инспектор на вкладку «Эффекты», чтобы её можно было заполнить, не выбирая вкладку вручную;
- **Дублировать** (`duplicateNode()`) — глубокая копия узла (тот же приём, что у Ctrl+C/Ctrl+V, но для одного узла сразу из меню): смещённая позиция, новый id, стартовый триггер копии сбрасывается (двух стартовых узлов быть не может), исходящие переходы копии ведут на ТЕ ЖЕ цели, что и у оригинала, но собственными id choice-строк — правка перехода в одной копии не задевает другую.

**Инлайн-правка названия** (`startInlineTitleEdit()` в `03-canvas.js`) — двойной клик по заголовку узла прямо на карточке холста показывает поверх нужного места плавающий `<input>` (не `contenteditable` на самой карточке — карточка целиком перерисовывается при любом `renderAll()`, а отдельный элемент поверх это спокойно переживает). Enter/потеря фокуса — сохранить, Escape — отменить без изменений.

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа T): пункт бэклога про «главные зоны интерфейса — Navigator/Canvas/Inspector/Checks» не потребовал отдельного кода — этим зонам инструмент и так соответствует с самого начала (левая панель/холст/правая панель/список проверок), это уже случившийся факт архитектуры, а не отдельная задача. Контекстное меню на пустом месте холста (например, «Добавить узел здесь») — не заводилось: бэклог просил меню на узле и на переходе, не на пустом холсте, а лишний третий вариант меню ради симметрии не был бы использованием, которое кто-то просил.

## 25. Runtime-состояние узла, человекочитаемое превью, тест из произвольной точки

**Runtime-состояние узла** (`nodeRuntimeState()`/`rtStateDotHtml()` в `03-canvas.js`, цветной кружок на карточке холста и в списке узлов) — чисто структурная классификация ПО ГРАФУ, без живого прогона: как именно узел входит в игру, а не что у него происходит дальше.
- 🟢 **Доступен** — узел не заперт условием и достижим по переходам (или это старт/фоновый узел).
- 🔵 **По условию** — вход в узел зависит от `trigger.all` (мировых переменных), а не просто от того, что в него ведёт переход.
- 🔴 **Недостижим** — узел с `trigger.kind:'conditions'`, до которого не ведёт НИ ОДИН переход ни от одного другого узла (тот же тест, что уже был у фильтра статуса «Недостижимые», §5, — просто теперь ещё и видимый прямо на карточке, а не только в списке проверок).
- 🟠 **Концовка** — у узла заполнено `ending` (проверяется первым — концовка остаётся концовкой независимо от остального).

Дед-энд (⛔ — нет исходящих переходов и не концовка) сознательно НЕ включён в эту классификацию, хотя формально тоже «runtime-состояние»: дед-энд и «по условию» не исключают друг друга (узел может быть заперт условием И при этом не вести никуда дальше), а объединение в одно поле заставляло бы каждый раз терять один из двух фактов ради показа другого. У дед-энда уже есть свой отдельный, годами работающий значок (⛔) — здесь он просто не дублируется.

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа U): состояния «Пройден»/«Провален» (`completed`/`failed`) из исходного пункта бэклога — это по своей природе состояния КОНКРЕТНОГО прохождения (какие узлы посетил ИМЕННО этот запуск, чем он закончился), а не факты о графе как таковом. Story Map — авторский инструмент, а не живая игровая сессия: единственное место, где вообще существует «прохождение», — это как раз лёгкий inline-симулятор («▶ Играть», §18/ниже), и там это уже есть — в виде журнала прогона (какие узлы посещены, чем закончилось). Постоянная пометка узлов на СТАТИЧНОМ графе как «пройден» смешала бы «что задумано» с «что случилось один раз при одном тестовом прогоне» — путаница хуже отсутствия функции.

**Человекочитаемое превью условий/эффектов** (`condListPreviewText()` в `04-inspector.js`) — одна строка прямо над списком строк-редакторов внутри `condRowsHtml()` (использует его вкладка «Доступность» узла, «Эффекты» узла, `requires`/`effects` перехода — все четыре места сразу, так как правится одна общая функция): «Если Опасность ≥ 5» для условий, «Меняет: Опасность +2» для эффектов. Пустой список — без строки (нечего суммировать). Тот же принцип уже был у `nodeTriggerSummary()` (§20, Обозреватель триггеров) для триггера узла целиком — здесь он обобщён на любой список строк, включая `requires` перехода, которого раньше это не касалось.

Условия и эффекты уже были структурными объектами `{var,op,value}` (а не вольным текстом) задолго до этой группы — «структурная модель вместо строк» из исходного пункта бэклога уже выполнена архитектурой инструмента с самого начала, отдельной задачи здесь не было. Сознательно **не реализовано**: переименование полей в `subject`/`operator`/`value` (как буквально просил пункт бэклога) — `var`/`op`/`value` это тот же самый смысл другими словами, переименование затронуло бы десятки мест по всему коду ради нулевой функциональной разницы. Вложенные группы AND/OR вместо плоского списка (сейчас список condRowsHtml — всегда неявный AND, как и раньше) — тоже не заводились: это архитектурно большая, рискованная смена (парсер, рекурсивный UI, пересмотр логики Проверок/симулятора, миграция всех уже сохранённых плоских `all`-массивов) ради возможности, которой ни разу не понадобилось ни в одном уже собранном сюжете.

**Тест из произвольной точки входа** (`simStartFrom()` в `14-simulation.js`, пункт контекстного меню узла «🧪 Тест отсюда», §24) — та же машина прогона, что и обычная «▶ Играть» (`simStart()` теперь просто зовёт `simStartFrom(startNode.id)`), но с любого узла графа, а не только с настоящего старта. Модалка честно показывает баннер «🧪 Тестовый запуск не с начала игры», когда точка входа — не `trigger.kind:'start'`, чтобы не перепутать тестовый прогон с настоящим прохождением. «Заново» (`btnSimRestart`) перезапускает С ТОЙ ЖЕ точки входа, что и был запущен этот прогон (`simEntryNodeId`), а не тайно перескакивает на настоящий старт.

Значения переменных в панели «Переменные» во время прогона теперь редактируемые (`<input>` вместо простого текста) — это и есть «тест с заданным состоянием» из исходного пункта бэклога, только гибче отдельного диалога «задать состояние перед стартом»: можно поменять любую переменную в ЛЮБОЙ момент прогона (не только при входе) и сразу увидеть, как это меняет доступность переходов, без пересборки сценария заново. Каждая ручная правка попадает в журнал отдельной строкой («🔧 …изменено вручную») — прогон не должен выглядеть так, будто игра сама довела переменную до этого значения.

Сознательно **не реализовано**: детерминированный seed для случайных чисел — у лёгкого inline-симулятора Story Map (в отличие от полноценного story-bot, `10-Story-Bot.md`) НЕТ никакой случайности вообще (`sim.dangerChance` — метаданные для бота, сама симуляция их не бросает и не потребляет), поэтому прогон из одной и той же точки с одним и тем же состоянием переменных и одними и теми же выборами игрока УЖЕ полностью детерминирован — заводить seed было бы решением несуществующей проблемы.

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа U): Probability/Balance Preview со ссылкой на централизованный `probability_id` — такой системы (централизованного словаря вероятностей/баланса с id) нигде в репозитории не существует; сам пункт бэклога прямо просит «не дублировать баланс внутри Story Map», а строить новую систему баланса с нуля ради того, чтобы тут же на неё сослаться, значило бы придумать то, что было прямо запрещено придумывать.

## 26. Жизненный цикл сущности, автономные события мира

**Жизненный цикл сущности** (`entity.lifecycle`, `ENTITY_LIFECYCLE_STATES` в `01-core-utils.js`, select на карточке сущности) — `planned`/`active`/`dead`/`destroyed`/`removed`/`archived`, про судьбу сущности ВНУТРИ игрового мира («персонаж погиб», «предмет уничтожен»). Пусто по умолчанию (не каждая сущность нуждается в этом — не плодим шум на карточке каждой мелочи), показывается бейджем в списке сущностей рядом с названием, когда задано.

Это ОТДЕЛЬНОЕ поле от уже существовавшего `entity.status` (`'active'`/`'deprecated'`, §13) — тот про АВТОРСКИЙ архив («эту сущность мы больше не используем в дизайне», влияет на подсказки/Orphan Detection/каскадное удаление), `lifecycle` — про то, что происходит с сущностью ВНУТРИ придуманного мира, и никак не влияет на архивирование, подсказки автодополнения или проверки. Сущность может быть одновременно `status:'active'` (всё ещё используется в дизайне) и `lifecycle:'dead'` (персонаж погиб по сюжету) — это два разных, не путающихся друг с другом факта.

**Автономные события мира** (`worldEvents`, `09-world-model.js`/`10-world-view.js`, группа слева «Автономные события мира») — что происходит БЕЗ участия игрока: `actor` (сущность, кто действует) → `action` (свободный текст — «нападает на», «заражает») → `target` (сущность, на кого), плюс необязательный `resultLifecycle` (какой lifecycle получил бы `target`, если событие «случилось») и `effects` (тот же формат `{var,op,value}`, что и везде — `condRowsHtml`/`condListPreviewText`, §25). Список и детальный редактор — та же центральная панель `#entityDetail`, что и у сущности/идеи, взаимоисключающе через `selectedWorldEventId` (тот же принцип, что уже развёл entity/proposal, §15). Карточка каждой участвующей сущности (и `actor`, и `target`) показывает обратную ссылку — «Автономные события мира (N)» — клик по строке открывает событие.

Это **декларативные** записи для дизайна и трассировки («рейдеры периодически нападают на бункер, это портит запасы и может убить NPC»), а не часть игрового цикла: `resultLifecycle` НЕ применяется автоматически к `target` — это справочная пометка «вот что случилось бы», которую дизайнер при желании переносит на карточку сущности вручную (когда решает, что событие действительно произошло по сюжету). Effects точно так же не «стреляют» сами — это не более чем структурированная запись того, что МЕНЯЛОСЬ БЫ.

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа V): живое срабатывание автономных событий внутри lightweight-симулятора («▶ Играть», §18/§25) — у симулятора вообще нет модели времени/мира вне графа choices, в которую это можно было бы честно встроить, не изобретая по сути отдельный игровой движок внутри Story Map (то же ограничение, что уже отмечено у фоновых узлов, §18: условные узлы тоже не активируются сами по себе). `conditions` на событие мира (когда оно «может» сработать) — тоже не заводились: без реального срабатывания условия были бы чисто декоративны, только усложняя форму без пользы. Третий полноценный режим-вид «Consequence Graph» (переключаемый вместе с «Сюжет»/«Мир»/«Таймлайн», как просил исходный пункт бэклога) — не заводился: то, что он должен показывать («что меняется в мире»), уже доступно через несколько уже построенных поверхностей — цепочка последствий выбора (`consequenceChainHtml()`, §20), Dependency Explorer сущностей/переменных (обе стороны использования) и теперь кросс-ссылка «участвует в N событиях мира» на карточке сущности; строить ради того же самого ещё один полноэкранный граф-рендер значило бы дублировать уже отвечающие на этот вопрос инструменты, а не добавлять новую способность.

## 27. Производительность: перетаскивание без пересборки DOM

**Найденная и исправленная ошибка (не из бэклога, попутно)**: `snapshot()`/`restoreSnapshot()` (история отмены/возврата) не включали `worldEvents`, добавленные группой V, — `Ctrl+Z`/`Ctrl+Shift+Z` молча не отменяли правки автономных событий мира, хотя комментарий над этими функциями прямо обещает «одну историю на оба слоя». Исправлено — `worldEvents` теперь часть снимка, как и всё остальное.

**Быстрый путь перетаскивания** (`updateNodeBoxPositions()`/`updateStickyNotePosition()`/`renderEdgesOnly()` в `03-canvas.js`) — единственная РЕАЛЬНАЯ, легко продемонстрированная проблема производительности в инструменте: перетаскивание узла или заметки вызывало `renderCanvas()` на КАЖДЫЙ `pointermove` (десятки раз в секунду), а `renderCanvas()` пересобирает `innerHTML` ВСЕХ карточек узлов и ВСЕХ рёбер графа с нуля — притом что реально сдвинулся один (или несколько выделенных) узел, а не весь граф. Теперь во время активного перетаскивания:
- позиция самой карточки узла/заметки обновляется напрямую через `style.left`/`style.top` на уже существующем DOM-элементе (без пересборки её содержимого — бейджи/название/переходы не менялись, их незачем перерисовывать);
- рёбра всё равно перерисовываются целиком (`renderEdgesOnly()`, вынесенная в отдельную функцию половина прежнего `renderCanvas()`) — их путь (`d` у `<path>`) зависит от позиции узлов, а вычислять адресно, каких именно рёбер коснулось перетаскивание, не окупилось бы;
- миникарта/размеры `#edgeLayer` не трогаются на каждый пиксель — досчитываются один раз в момент отпускания кнопки мыши (`applyWorldTransform()` в обработчике `pointerup`), а не при каждом промежуточном сдвиге.

Сама позиция по-прежнему коммитится в историю отмены/возврата ровно один раз за весь жест (`commitMove()`/`commitStickyMove()`, как и раньше) — быстрый путь меняет только КАК часто и КАК ИМЕННО обновляется экран во время перетаскивания, а не когда фиксируется сама правка.

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа X) — вся остальная, более общая часть пункта:
- **Viewport culling / lazy rendering для World Graph** — не заводились: ни то, ни другое не решает продемонстрированную проблему (она была именно в перетаскивании, а не в первоначальной отрисовке), а решают гипотетическую — на графах реалистичного для ОДНОЙ игры размера (десятки-сотни узлов/сущностей) полная пересборка `innerHTML` при обычном рендере (не при перетаскивании) занимает миллисекунды, не заметные глазом. Строить culling значило бы ещё и переписать интерактивные проверки, которые сейчас честно полагаются на присутствие ВСЕХ узлов в DOM разом (`connectTargetIdAt()`, рамка выделения) — большой рискованный рефакторинг ради проблемы, которую ничто не подтверждает.
- **Snapshot перед bulk-операциями = один undo step** — уже было: `importIdea()` (импорт идеи + авто-связи) и `deleteSelectedNodes()` (массовое удаление) уже вызывают `pushHistory()` ровно один раз на всю операцию, а не на каждый затронутый узел.
- **Предупреждение/лимит перед массовыми auto-link** — уже было (группа H): `LINK_FANOUT_CAP=30` в `applyAutoLinks()` (`07-idea-import.js`) — даже строже, чем «предупреждение при 500+» из исходного пункта: лишние автосвязи не создаются вовсе, а не просто предупреждают постфактум.
- **Recovery после ошибочной bulk-операции** — уже было: то же самое `Ctrl+Z`, что и для любой другой правки (и теперь гарантированно покрывает оба слоя, см. исправленную ошибку выше).
- **Атомарное сохранение** — уже было, отмечено уже в самом пункте бэклога.
- **Автобэкап перед импортом, schema validation при открытии, миграция старых проектов** — все три уже сделаны группой S (`backupCurrentStateBeforeImport()`, `readStoryJsonWithRecovery()`, `STORY_SCHEMA_VERSION`/`migrateStoryData()`, §23) — этот пункт бэклога описывает ту же самую задачу другими словами, реализованную раньше, чем до него дошла очередь по алфавиту.

## 28. Decision Log

**Decision Log** (`decisions`, `09-world-model.js`/`10-world-view.js`, группа слева «Decision Log») — записи о РЕШЕНИЯХ по архитектуре/дизайну («почему раздел устроен именно так»), а не о содержимом сюжета (это уже `proposals`, §15) и не о конкретной вещи в игровом мире (это `entities`). Каждая запись — заголовок, текст, `status`, `source`, необязательные связанные системы/сущности (те же `chipPickerHtml`, что и у `proposals`) и комментарий. Список и детальный редактор — та же центральная панель `#entityDetail`, что и у сущности/идеи/события мира, взаимоисключающе через `selectedDecisionId` (тот же принцип, что уже развёл entity/proposal/worldEvent, §15/§26).

**`status`** (`defined`/`tentative`/`unknown`/`deprecated`) — насколько решение устоялось. `'unknown'` — ПЕРВОКЛАССНЫЙ статус, а не «забыли заполнить»: Master Design сам иногда сознательно оставляет вопрос открытым, и Story Map не должен заставлять фиксировать ответ раньше времени — «не определено (осознанно)» так и читается в интерфейсе, отдельно от пустого/незаполненного поля.

**`source`** (`master-design`/`object-plan`/`story`/`prototype`/`decision`) — откуда взялось решение: продиктовано Master Design-документом, решено внутри Object Plan, решено в самом Story Map, родилось из прототипа, или отдельное ситуативное решение без более общего источника. Панель Decision Log содержит прямую ссылку на сам файл Master Design (`../postapocalyptic_survival_master_game_design.md` — открывается как обычный локальный файл, раз Story Map и так работает как `file://`) и ссылку «Открыть Object Plan» (`../object-plan/index.html`, открывает инструмент, а не конкретный пункт в нём — см. ниже, почему не глубже).

**Change Impact** (`decisionChangeImpact()`) — не отдельный пересчёт, а СИНТЕЗ уже существующих кросс-ссылок (§14/§26): для каждой сущности из `relatedEntities` решения суммирует, сколько узлов сюжета на неё ссылаются (`nodesReferencingEntity()`, плюс `nodesUsingCatalogEntity()` для каталожных сущностей), сколько связей мира её касается (`relationsForEntity()`) и в скольких автономных событиях мира она участвует (`worldEventsForEntity()`). Показывается прямо на карточке решения одной строкой — «затрагивает N узлов / M связей / K событий» — вместо отдельного экрана.

Обратная сторона той же связи — карточка сущности показывает «Затронуто решениями (N)»: список решений, где эта сущность упомянута в `relatedEntities`, с кликабельным переходом к решению. Decision Log участвует и в Orphan Detection сущностей (§22) наравне с узлами/связями/событиями мира/идеями — сущность, упомянутая только в Decision Log, уже не считается «нигде не используется».

Сознательно **не реализовано** (см. `11-Story-Map-Backlog.md`, группа Y):
- **Отдельная страница «Architecture»** — не заводилась: тот же принцип, что и у Обзора проекта (§23) и у отказа от лишних режимов-видов (§26) — список+карточка в уже существующей структуре Мира не хуже отдельной страницы, а ещё одно исключение из «инструмент без роутинга» не окупается.
- **Глубокая ссылка «Open in Object Plan» на конкретный пункт** — сознательно НЕ реализовано: Object Plan не имеет никакого механизма выбора элемента по URL (ни `location.search`, ни `location.hash`), и городить его специально означало бы менять чужой инструмент, который весь этот бэклог до сих пор трогал только на чтение (Object Plan — read-only зависимость Story Map, а не то, что этот проект правит). Ссылка ведёт на сам инструмент, честно, без притворства, что она «открывает именно то самое».
- **`Where used?` как отдельная универсальная функция «везде»** — не заводилась отдельно: у каждого типа сущности (переменные, узлы, World-сущности, теперь и решения) уже есть СВОЙ Dependency Explorer/кросс-ссылка (§1/§14/§20/§26/выше) под свою форму данных — единая абстрактная «найди, где это используется» на все типы разом усложнила бы код ради внешнего единообразия, не добавив ничего, чего каждый из них уже не показывает по отдельности.

## 29. Итоговая архитектура (закрытие бэклога)

Последняя группа исходного бэклога (`11-Story-Map-Backlog.md`, группа Z, п. 400–405) — не список задач, а НАПРАВЛЕНИЕ: «не добавлять новых крупных сущностей — следующий этап есть связывание уже существующих систем», с целевой схемой `STORY → WORLD/VARIABLES/ACTIONS → CONSEQUENCES → WORLD STATE → FUTURE EVENTS`, где Object Plan отвечает на «что нужно построить, чтобы этот мир и эти события могли существовать». Это не отдельная задача на реализацию — это проверка того, что уже построено группами A–Y, действительно складывается в эту цепочку, а не в набор нескольких изолированных функций. Складывается:

- **STORY** — граф узлов/переходов (§1–§9), режим «Сюжет».
- **WORLD/VARIABLES/ACTIONS** — слой «Мир»: типизированные сущности (§12), включая каталожные ссылки на предметы/навыки/действия/системы Object Plan (§13/§21), мировые переменные (§1), структурная связка «Действие → Цель» (`node.actionRef`, §21).
- **CONSEQUENCES** — структурные эффекты `{var,op,value}` на переменные и на entity-lifecycle (§25/§26), цепочка последствий выбора (`consequenceChainHtml()`, §20), Change Impact (§28) — «что изменится, если это решение/эта сущность поменяется».
- **WORLD STATE** — жизненный цикл сущности (`entity.lifecycle`, §26), значения мировых переменных, связи между сущностями (§12/§14).
- **FUTURE EVENTS** — фоновые узлы по расписанию (`trigger.kind:'scheduled'`, §17/§18) и автономные события мира без участия игрока (`worldEvents`, §26) — то, что происходит дальше вне прямого выбора игрока.

Object Plan как ответ на «что нужно построить» — уже реализованная (не новая) сторона границы между инструментами: Story Map читает его каталоги (предметы/навыки/действия/системы, §13), его собственный статус реализации предмета (§22) и его игровые системы (§22), но никогда не пишет в него и не дублирует его данные — только ссылается (`ref.refId`) или связывает (`decisions[].relatedSystems`, §28).

Сознательно **не делалось** ничего нового для этой группы — сама она прямо просит не добавлять новых крупных сущностей. Единственная работа здесь — подтвердить, что цепочка уже целая, и явно её описать (этот раздел), а не строить ещё один слой поверх уже построенных пяти.

Этим закрыт весь `11-Story-Map-Backlog.md` — все 405 пунктов разобраны по группам A–Z, каждая отмечена ✅/❌ с обоснованием того, что сделано, что сознательно не сделано и почему.

## 30. Русские типы связей по умолчанию, чтение кастомных предметов Object Plan (`store.custom`)

Уже после закрытия бэклога — по прямому запросу автора после того, как он начал сам пользоваться инструментом («нужно всё, что написано на английском рядом, делать на русском, либо на русском в UI и пусть в json остаётся на английском»).

**Типы связей по умолчанию — теперь на русском.** `DEFAULT_RELATION_TYPES` (`09-world-model.js`) при создании нового проекта сеет типы связей русскими именами (`состоит_в`/`включает`, `друг_с`, `поддерживает_действие`, и т. д. — было `member_of`/`has_member`, `friend_of`, `supports_action`…). Для **уже существующих** проектов со старыми английскими именами это не мигрируется автоматически — переименование сделано осознанным разовым действием пользователя (кнопка «🌐 Известные — на русский», `#btnTranslateRelTypes`, вызывает `translateRelationTypesToRussian()`), а не тихой автомиграцией при загрузке файла: тип связи — авторские данные, пользователь мог сам придумать/переименовать свои типы, и молча переписывать их имена при каждой загрузке было бы неожиданным и потенциально разрушительным для его собственной правки. Функция сверяет текущее имя/обратное имя типа с таблицей известных английских→русских соответствий (`RELATION_TYPE_RU_TRANSLATIONS`) и переименовывает только совпавшие — остальные (в том числе уже переведённые или придуманные пользователем) не трогает; безопасный повторный запуск (идемпотентна, можно нажимать сколько угодно раз). Переименование в любом случае ничего не ломает: связь (`relations[].type`) всегда ссылается на внутренний `id` типа, а не на строку `name` (см. «Стабильные id», §13) — так что смена имени в любой момент не портит уже существующие связи, ни в `story.json`, ни в ранее импортированных идея-бандлах.

**Действия Object Plan (`ACTIONS`, например `SLEEP`) остаются на английском** — это честное, задокументированное ограничение, а не забытая часть задачи: у `ACTIONS` в самом Object Plan (`object-plan/js/02-vocab.js`) нет никакого русского названия — это плоский массив голых строк без отдельного поля-метки. Story Map принципиально не редактирует и не дублирует данные Object Plan (см. §29), поэтому подставить русскую подпись самостоятельно, без изменений в Object Plan, невозможно — только показать как есть.

**Story Map теперь также читает кастомные предметы Object Plan (`store.custom`).** У Object Plan два источника предметов: встроенный статический каталог `PLAN_ITEMS` (шитый в код через `addItems()` в `02-vocab.js`/`03-data-shelter.js`/…) и `store.custom` — предметы, добавленные самим пользователем через собственную функцию Object Plan «добавить свой объект», которые сохраняются только в `data/object_plan.json` (поле `custom`, пишется `saveStoreToProject()` в `object-plan/js/07-store.js`). Раньше Story Map видел только первый источник. Новая функция `allPlanItems()` (`09-world-model.js`) на чтении объединяет оба — встроенный каталог плюс `objectPlanStatusData.custom` (тот же файл, что Story Map уже читал раньше для статуса реализации предмета, §22, лучшая попытка, без гарантии — если файла нет, `custom` просто пуст) — и используется везде, где раньше читался напрямую `PLAN_ITEMS`: пикер предмета (`catalogOptionsFor('items')`, `chipOptionsFor('items')`), поиск предмета по id (`findPlanItem()`), вычисление типов ресурсов (`getResourceTypes()`, §21). Изменение только на чтении, без нового поля в `story.json` — `story.json`-у не нужна отдельная миграция/версия схемы. Практический эффект: если добавить в Object Plan, например, «Спальник» как альтернативу «Кровати» для действия `SLEEP`, он появится в выпадающих списках предметов Story Map (после перезагрузки Story Map — оба инструмента читают/пишут независимо, без live-синхронизации между открытыми вкладками).

**Кнопка «🔄 Object Plan» в шапке** (`refreshObjectPlanData()`, `09-world-model.js`) — та же перезагрузка `data/object_plan.json`, что и раньше происходила только при подключении/восстановлении папки проекта (`loadStoryFromProject()`, §6), но по кнопке и без переподключения папки целиком: если папка уже подключена, `loadObjectPlanStatus()` просто перечитывает тот же файл ещё раз (`readJsonFromProject`, тот же самый вызов) и перерисовывает экран — так можно увидеть новый статус реализации или новый `store.custom`-объект, добавленный в Object Plan уже ПОСЛЕ того, как Story Map был открыт, без риска потерять несохранённые правки сюжета/мира (полное переподключение папки такого риска не несёт технически, но лишний диалог выбора папки не нужен для того, что можно сделать одним кликом). Без подключённой папки кнопка ничего не делает и просит подключить папку — то же сообщение, что у «💾 Прогресс в проект» в Object Plan.
