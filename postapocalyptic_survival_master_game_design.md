# Постапокалиптическое выживание --- Master Game Design Map

> Единая интеллектуальная карта концепции, игровых систем, контента и
> связей между ними.
>
> Документ фиксирует существующие идеи проекта и отдельно отмечает
> места, которые пока не определены окончательно.

------------------------------------------------------------------------

# 1. КОНЦЕПЦИЯ ИГРЫ

## 1.1 Жанровое ядро

2D постапокалиптическая survival/simulation игра, в которой игрок
начинает с небольшого убежища, управляет ресурсами и группой, физически
исследует внешний мир, находит предметы и людей, принимает решения и
постепенно создаёт устойчивую систему выживания.

Ключевые направления:

-   выживание;
-   управление убежищем;
-   физическое исследование;
-   поиск ресурсов;
-   персонажи и отношения;
-   мораль и последствия;
-   независимые фракции;
-   динамический мир;
-   крафт и строительство;
-   здоровье, травмы и болезни;
-   смерть с постоянными последствиями.

Атмосферно проект частично опирается на ощущения от This War of Mine, но
делает упор на более свободное физическое исследование и независимый
мир.

## 1.2 Главный принцип

**Игрок не является центром мира.**

Мир должен существовать самостоятельно:

-   люди перемещаются;
-   группы добывают ресурсы;
-   фракции торгуют и воюют;
-   NPC решают собственные проблемы;
-   происходят случайные события;
-   знакомые территории меняются;
-   персонажи могут погибать;
-   отношения меняются;
-   мир продолжает работать без игрока.

Игрок --- один из факторов мира.

## 1.3 Долгосрочная цель

Игрок:

1.  выживает;
2.  развивает убежище;
3.  формирует группу;
4.  исследует мир;
5.  находит ресурсы и новые территории;
6.  встречает людей;
7.  узнаёт историю мира;
8.  принимает решения;
9.  сталкивается с последствиями;
10. при необходимости меняет основное убежище.

# 3. УБЕЖИЩЕ / БУНКЕР

## 3.1 Стартовое убежище

Игрок начинает в небольшом подземном убежище.

Минимальная конфигурация:

-   несколько жилых комнат;
-   базовые предметы для выживания.

Стартовое убежище ограничено и заставляет решать:

-   что хранить;
-   что использовать;
-   что ремонтировать;
-   что строить;
-   куда тратить материалы;
-   когда выходить наружу.

## 3.2 Бункер как система

Бункер связан с:

-   ресурсами;
-   водой;
-   энергией;
-   хранением;
-   персонажами;
-   строительством;
-   ремонтом;
-   крафтом;
-   безопасностью;
-   временем;
-   событиями;
-   смертью;
-   автономностью NPC.

## 3.3 Развитие

Игрок может строить, ремонтировать, улучшать, устанавливать
оборудование, организовывать хранение и создавать производственные
возможности.

## 3.4 Смена убежища

В мире можно найти:

-   более крупный бункер;
-   лучше оборудованное убежище;
-   убежище с другими выжившими;
-   заброшенный объект для восстановления.

Игрок может сменить основное убежище. Переселение должно быть значимым
стратегическим решением.

# 4. ВНЕШНИЙ МИР

## 4.1 Физическое исследование

Игрок не выбирает локации через меню.

Вместо:

``` text
Бункер → Локация A → Локация B
```

используется:

``` text
Бункер
↓
персонаж выходит
↓
идёт по миру
↓
достигает места
```

Игрок выбирает персонажа и задаёт точку движения.

## 4.2 Многоуровневый 2D-мир

Мир строится из связанных 2D-сцен:

``` text
Бункер
↓
Главная трасса
↓
Развилка / указатель
↓
Город
↓
Городская дорога
↓
Дверь дома
↓
Сцена дома
↓
Город
↓
Край города
↓
Главная трасса
```

Переходы происходят через физические объекты:

-   двери;
-   края территории;
-   лестницы;
-   входы;
-   указатели.

Игра не спрашивает игрока «войти или нет» --- игрок сам нажимает на
визуальный объект.

## 4.3 Fast Travel

Первое прохождение территории должно быть физическим. После исследования
важных мест может открываться быстрое перемещение. Точные правила пока
не определены.

# 5. COLLISION, NAVIGATION И INTERACTION

Эти системы должны быть разделены.

## Collision

Физическое препятствие:

-   стены;
-   мебель;
-   закрытые двери;
-   твёрдые предметы.

Базовая прямоугольная collision подходит для большинства объектов. В
текущем Part Editor предусмотрена AUTO collision по непрозрачной области
изображения.

## Navigation / Walkable

Определяет доступную область перемещения.

## Pathfinding

Команда «иди туда» должна приводить к построению пути вокруг
препятствий.

## Interaction Point

Персонаж подходит не в центр объекта, а к допустимой точке
взаимодействия.

``` text
Игрок выбрал действие
↓
Interaction Point
↓
Pathfinding
↓
персонаж подходит
↓
Action
↓
Animation
```

Главная связка:

``` text
Collision
↓
Navigation
↓
Pathfinding
↓
Interaction Point
↓
Action
↓
Animation
```

# 6. ПЕРСОНАЖИ И ВЫЖИВШИЕ

## 6.1 Принцип

Персонажи не являются классами. Каждый человек --- отдельная личность.

Персонаж имеет:

-   предысторию;
-   характер;
-   склонности;
-   сильные и слабые стороны;
-   навыки;
-   потребности;
-   здоровье;
-   отношения;
-   инвентарь;
-   экипировку;
-   текущее действие;
-   автономность / AI.
-   все навыки можно развивать и прокачивать

## 6.2 Навыки

Возможные направления:

-   медицина;
-   строительство;
-   ремонт;
-   готовка;
-   крафт;
-   поиск ресурсов;
-   исследование;
-   оружие;
-   скрытность;
-   физическая работа.

Каждый может выполнять большинство задач, но эффективность различается в начале,  и в зависимости от прокачки можно улучшить.

## 6.3 Состояния

Потенциальные параметры:

-   Health;
-   Hunger;
-   Thirst;
-   Energy;
-   Injuries;
-   Illness;


## 6.4 Автономность

Персонажи могут самостоятельно:

-   есть;
-   пить;
-   спать;
-   лечиться;
-   искать воду/еду;
-   выполнять другие базовые потребности.

Команда игрока имеет более высокий приоритет.

# 8. ЭНЕРГИЯ

У объектов может быть собственный энергетический контур.

Примеры:

``` text

Аккумулятор → машина → работает на машину
Солнечная панель → бункер → производит энергию
```

Источники:

-   аккумуляторы;
-   солнечные панели;
-   ветрогенераторы;
-   велогенераторы;
-   другие источники.

Панели могут ломаться и загрязняться.

Потребители:

-   свет;
-   лампы для урожая;
-   станки;
-   холодильник;
-   другое оборудование.

Система рассчитывает:

``` text
производство
+
накопление
-
потребление
=
баланс
```

Панель убежища может показывать приход, расход, баланс и запас.

# 10. РЕСУРСЫ, INVENTORY И STORAGE

Ресурсы — это одна из основных экономических систем игры.

Они используются для:

* поддержания жизни персонажей;
* лечения;
* строительства;
* ремонта;
* крафта;
* работы оборудования;
* развития убежища;
* обеспечения энергией и водой;
* обмена и торговли;
* выполнения некоторых действий и событий.

Главный принцип: **ресурсы не должны быть привязаны к конкретному объекту или системе.** Один и тот же ресурс может находиться в инвентаре персонажа, в ящике, на складе, в машине, в контейнере или в другом объекте.

---

# 10.1. Жизнеобеспечение

Это ресурсы, которые непосредственно связаны с выживанием людей и поддержанием их состояния.

## Еда

Основные категории:

* готовая еда;
* сырые продукты;
* мясо;
* рыба;
* овощи;
* фрукты;
* зерно/крупы;
* консервы;
* хлеб и другие мучные продукты;
* сухие продукты;
* продукты длительного хранения;
* вода как отдельный ресурс;
* ингредиенты для приготовления еды.

Дополнительно предметы еды могут иметь:

* пищевую ценность;
* количество порций;
* срок хранения;
* состояние;
* необходимость приготовления;
* возможность испортиться.

Например:

```text
Консервы
↓
готовая еда
↓
долгое хранение
```

или:

```text
Сырое мясо
↓
требует приготовления
↓
готовая еда
```

Конкретный окончательный список продуктов пока не фиксируется.

---

# 10.2. Вода

Вода является отдельным жизненно важным ресурсом.

В отличие от обычного предмета, вода может существовать как **количество ресурса внутри объекта**.

Например:

```text
Бочка
Water
Capacity: 200 L
Amount: 150 L
```

Источники:

* дождь;
* резервуар;
* бочка;
* водонапорная башня;
* скважина;
* водопровод;
* найденная ёмкость;
* другие источники.

Вода может иметь состояние:

* чистая;
* загрязнённая;
* отравленная;
* другие состояния в будущем.

Вода используется для:

* питья;
* приготовления еды;
* других бытовых процессов;
* потенциально выращивания растений;
* других механик, которые будут добавлены позже.

---

# 10.3. Медикаменты

Медицинские ресурсы используются для восстановления здоровья и лечения различных состояний.

Категории:

* лекарства;
* обезболивающие;
* антибиотики;
* перевязочные материалы;
* бинты;
* антисептики;
* средства для обработки ран;
* медицинские наборы;
* препараты для лечения конкретных заболеваний;
* другие медицинские предметы.

Также могут существовать:

```text
Medical Kit
First Aid Kit
Bandage
Medicine
Antiseptic
```

Медицинские предметы могут иметь разные назначения.

Например:

```text
Бинт
→ кровотечение / рана

Антисептик
→ обработка раны

Лекарство
→ заболевание

Медицинский набор
→ комплексное лечение
```

Точные эффекты и список заболеваний будут определяться отдельно.

---

# 10.4. Другие расходуемые ресурсы жизнеобеспечения

Помимо еды, воды и медикаментов, сюда могут относиться:

* топливо;
* средства для приготовления пищи;
* предметы гигиены;
* бытовые расходники;
* средства очистки воды;
* средства очистки помещений;
* предметы для ухода за растениями;
* другие расходуемые предметы.

Здесь важно различать:

**ресурс** и **предмет**.

Например:

```text
Вода
→ ресурс

Бутылка воды
→ предмет, содержащий воду
```

или:

```text
Топливо
→ ресурс

Канистра
→ контейнер с топливом
```

Это позволит использовать одну архитектуру для разных типов хранения.

# 10.5. Технические ресурсы

Технические ресурсы не потребляются непосредственно для поддержания жизни, но необходимы для развития и функционирования убежища.

## Основные категории

### Материалы

Общая категория материалов для строительства и производства:

* строительные материалы;
* строительный мусор;
* плиты;
* панели;
* строительные заготовки;
* другие материалы.

### Дерево

Отдельный ресурс:

* доски;
* древесина;
* брусья;
* деревянные детали;
* другие деревянные материалы.

Используется для:

* строительства;
* ремонта;
* изготовления мебели;
* крафта;
* других деревянных конструкций.

### Металл

Возможные варианты:

* лом;
* металлические листы;
* трубы;
* металлические детали;
* проволока;
* стальные элементы;
* алюминиевые элементы;
* другие металлические материалы.

Используется для:

* строительства;
* ремонта;
* изготовления оборудования;
* изготовления инструментов;
* оружия;
* других технических объектов.


### Электронные компоненты

Отдельная категория:

* микросхемы;
* платы;
* лампы;
* электронные детали;
* аккумуляторные компоненты;
* другие электронные элементы.

Используются для:

* ремонта электрооборудования;
* создания оборудования;
* генераторов;
* освещения;
* автоматизации;
* других технических систем.

# 10.6. Топливо и энергетические ресурсы

Я бы выделил их в отдельную группу, потому что они находятся между жизнеобеспечением и техническими ресурсами.

Возможные ресурсы:

* бензин;
* дизельное топливо;
* другое топливо;
* аккумуляторный заряд;
* электрическая энергия.

При этом важно не смешивать:

```text
Аккумулятор
```

и

```text
Энергия внутри аккумулятора
```

Аккумулятор — предмет/объект.

Энергия — ресурс.

Например:

```text
Battery
Capacity: 1200 kWh
Amount: 850 kWh
```

# 10.8. Редкие и специальные ресурсы

Отдельно могут существовать ресурсы, которые не нужны постоянно, но используются для определённых целей:

* редкие компоненты;
* специальные детали;
* редкие химические вещества;
* уникальные материалы;
* сюжетные предметы;
* специальные ресурсы фракций;
* редкие технологические компоненты.

Такие ресурсы могут использоваться для:

* уникального оборудования;
* особых апгрейдов;
* редкого крафта;
* сюжетных действий;
* торговли.

Окончательный список не фиксируется.

```text
RESOURCES
```

# 10.10. Единое хранение

Все обычные предметы используют одну систему хранения.

Это означает, что один и тот же предмет может находиться:

```text
Персонаж
↓
Инвентарь

Ящик
↓
Storage

Шкаф
↓
Storage

Машина
↓
Storage

Бункер
↓
Storage

Труп
↓
Inventory / Loot
```

Базовые операции остаются универсальными:

```text
add_item(item_id, quantity)
remove_item(item_id, quantity)
```

Например:

```text
add_item("food_canned", 5)
```

или:

```text
remove_item("metal_scrap", 10)
```

Код не должен содержать:

```text
add_food()
add_water()
add_metal()
add_wood()
add_medicine()
```

если речь идёт об обычных предметах.

Вместо этого используется единая система предметов.

---

# 10.11. Ресурс и предмет — не всегда одно и то же

Это важное разделение.

Например:

```text
Бутылка воды
```

может быть обычным предметом:

```text
Item
├── Water
├── Amount
└── Container
```

Но:

```text
Резервуар
```

может иметь встроенное хранилище ресурса:

```text
Object
└── Resource Storage
    ├── Resource: Water
    ├── Capacity: 5000 L
    └── Amount: 3200 L
```

То же самое:

```text
Аккумулятор
└── Energy Storage
    ├── Capacity: 1200 kWh
    └── Amount: 850 kWh
```

Поэтому **не нужно превращать каждый литр воды или каждый киловатт энергии в отдельный Item**.

---

# 10.12. Масса и ёмкость

Значение:

```json
"maxWeight": 558
```

само по себе является просто **числом**.

В JSON нет информации о том, что `558` — это килограммы.

Единица измерения определяется тем, **какая система использует это значение и как его отображает интерфейс**.

Например:

```text
Inventory
maxWeight = 80
unit = kg
```

может отображаться:

```text
80 кг
```

А специализированное хранилище может использовать:

```text
Water
capacity = 5000
unit = L
```

и отображать:

```text
5000 L
```

Энергетическое хранилище:

```text
Energy
capacity = 1200
unit = kWh
```

и отображать:

```text
1200 kWh
```

То есть **число и единица измерения должны быть разделены**.

---

# 10.13. Почему это важно для конструктора

Конструктор не должен иметь отдельный код:

```text
вода
электричество
топливо
```

Лучше иметь универсальное понятие:

```text
RESOURCE STORAGE
```

Например:

```json
{
    "storage": {
        "resource": "water",
        "capacity": 5000,
        "unit": "L",
        "amount": 3200
    }
}
```

или:

```json
{
    "storage": {
        "resource": "energy",
        "capacity": 1200,
        "unit": "kWh",
        "amount": 850
    }
}
```

И уже интерфейс конструктора понимает:

```text
resource = water
→ показывать L

resource = energy
→ показывать kWh
```

Для обычного инвентаря:

```json
{
    "inventory": {
        "enabled": true,
        "slots": 20,
        "maxWeight": 80
    }
}
```

и интерфейс показывает:

```text
80 кг
```

Таким образом **один и тот же принцип хранения числового значения остаётся универсальным**, но единица измерения определяется контекстом.

# 10.14. Главный принцип

Не делать:

```text
WaterSystem
ElectricitySystem
FuelSystem
FoodSystem
MedicineSystem
```

только потому, что у ресурсов разные единицы измерения.

Лучше:

```text
Universal Resource
        │
        ├── Item
        ├── Inventory
        ├── Storage
        └── Resource Storage
```

А уже конкретный ресурс определяет:

```text
resource_id
unit
capacity
amount
consumption
production
```

Например:

```text
water
→ L
→ capacity
→ amount
→ consumption
```

```text
energy
→ kWh
→ capacity
→ amount
→ production
→ consumption
```

```text
fuel
→ L
→ capacity
→ amount
→ consumption
```

Это позволит одной архитектуре обслуживать **воду, энергию, топливо и будущие ресурсы**, не создавая отдельную систему для каждого из них.

## Лечение

Лечение выполняется через универсальную систему действий.

Персонаж может самостоятельно определить, что ему требуется лечение, если его текущее состояние требует медицинского вмешательства.

Для лечения персонаж проверяет доступность подходящего медицинского предмета.

Медицинский предмет может находиться:

* в собственном инвентаре;
* в другом доступном инвентаре;
* в хранилище;
* в медицинском шкафу;
* в медицинском контейнере;
* в другом объекте, доступном персонажу.

### Если подходящее средство есть в инвентаре

Персонаж:

1. определяет необходимость лечения;
2. проверяет собственный инвентарь;
3. находит подходящий медицинский предмет;
4. берёт его;
5. выполняет действие лечения;
6. расходует необходимое количество предмета;
7. получает соответствующий эффект лечения;
8. обновляет состояние здоровья;
9. при необходимости получает время восстановления;
10. завершает лечение.

### Если подходящего средства нет в инвентаре

Персонаж:

1. определяет необходимость лечения;
2. проверяет доступные хранилища;
3. ищет подходящий медицинский предмет;
4. определяет ближайшее доступное хранилище;
5. перемещается к нему;
6. открывает хранилище;
7. берёт необходимый предмет;
8. использует его;
9. расходует необходимое количество предмета;
10. получает эффект лечения;
11. обновляет состояние здоровья.

После лечения персонаж может:

* продолжить текущую задачу;
* вернуться к предыдущему действию;
* продолжить отдых;
* повторно лечиться, если требуется дополнительное лечение.

## Автономное лечение

Лечение не обязательно должно выполняться только прямым приказом игрока.

Если персонаж обладает автономностью и его состояние требует лечения, он может самостоятельно:

* обнаружить необходимость лечения;
* найти подходящий медицинский предмет;
* взять его из инвентаря;
* найти доступное хранилище;
* дойти до хранилища;
* взять медицинский предмет;
* использовать его;
* продолжить восстановление.

При этом **приказ игрока имеет более высокий приоритет**, чем автономное действие персонажа.

## Подходящий медицинский предмет

Лечение не должно быть привязано к одному конкретному предмету.

Система должна проверять:

* какой эффект требуется;
* какой тип травмы или заболевания нужно лечить;
* какие медицинские предметы подходят;
* есть ли подходящий предмет;
* сколько предмета требуется;
* можно ли использовать предмет в текущем состоянии персонажа.

Например, разные медицинские предметы могут использоваться для:

* лечения ран;
* остановки кровотечения;
* лечения инфекций;
* лечения заболеваний;
* уменьшения боли;
* восстановления здоровья;
* оказания первой помощи.

Конкретные предметы и их эффективность должны задаваться **данными**, а не отдельным кодом для каждого предмета.

## Связь лечения со временем

Лечение использует единую систему игрового времени.

Медицинское действие может иметь:

* время применения;
* время восстановления;
* длительность лечения;
* период действия препарата;
* время до следующего лечения;
* время полного восстановления.

Состояние персонажа продолжает изменяться во время лечения.

Например:

```text
Персонаж получил травму
        ↓
Система определяет состояние
        ↓
Требуется лечение
        ↓
Проверка инвентаря
        ↓
Есть подходящий предмет?
    ↓              ↓
   Да             Нет
    ↓              ↓
Использовать   Проверить хранилища
предмет             ↓
    ↓          Найти предмет
    ↓              ↓
    └──────→ Забрать предмет
                   ↓
             Использовать
                   ↓
             Эффект лечения
                   ↓
          Обновление состояния
                   ↓
        Восстановление со временем
```

### Важный принцип

**Персонаж не должен знать заранее, где находится конкретная аптечка.**

Он должен искать **подходящий предмет по требованиям лечения**.

Например:

```text
Требуется:
treat = bleeding

Система ищет:
item → подходит для bleeding
```

А не:

```text
если кровотечение:
    взять бинт_№1
```

Таким образом, в будущем можно добавлять новые аптечки, лекарства и медицинские предметы через данные, не изменяя саму систему лечения.

# 27. СМЕРТЬ

Смерть постоянна.

Погибший персонаж не просто удаляется.

После смерти остаётся объект останков.

С ним можно:

-   ничего не делать;
-   обыскать;
-   перенести;
-   похоронить;
-   сжечь.

Может существовать разложение.

Инвентарь и экипировка могут оставаться доступными.

Для NPC должны поддерживаться:

``` text
останки
выпадение инвентаря
выпадение экипировки
обыск
перенос
разложение
```

Смерть влияет на других персонажей через отношения.

``` text
близкий друг погиб
↓
сильная реакция
```

``` text
малознакомый погиб
↓
слабая реакция
```

Главный принцип:

``` text
Character dies
↓
останки
↓
инвентарь
↓
реакции
↓
мораль
↓
настроение
↓
отношения
↓
будущие события
```

# 29. ОТРАВЛЕНИЕ ЗАПАСОВ ВОДЫ

Резервуар воды является полноценным объектом мира.

Игрок может добавить яд в запас.

Необходимое количество может зависеть от объёма:

``` text
малый резервуар → меньше
большой резервуар → больше
```

Состояния воды пока не фиксируются окончательно.

Один звук должен переиспользоваться несколькими анимациями.

# 34. DATA-DRIVEN ПОДХОД

Главное правило:

> Код отвечает за то, как работает система. Данные отвечают за то, что
> это за объект.

Перед созданием новой механики нужно спросить:

``` text
Это новая система?
```

или:

``` text
Это данные / вариант уже существующей системы?
```

Приоритет:

``` text
новые данные
>
новая система
```

Графика отделена от логики.

Godot отвечает за:

-   AI;
-   логику;
-   navigation;
-   pathfinding;
-   выполнение действий;
-   анимации;
-   звук;
-   мировое поведение.

Конструкторы отвечают за:

-   данные;
-   графику;
-   ассеты;
-   JSON;
-   конфигурацию.

# 41. ФИНАЛЬНАЯ ФОРМУЛА

``` text
Универсальные данные
+
Физический 2D-мир
+

+
Независимые фракции
+
Единое время

+

Живой постапокалиптический survival-мир
```

Цель проекта --- не создать набор разрозненных механик.

Цель --- создать систему, в которой одна механика естественно порождает
последствия в других.

Пример:

``` text
Игрок нашёл другой бункер
↓
там живёт группа
↓
складываются отношения
↓
человек присоединяется
↓
его потребности входят в систему группы
↓
он использует воду и еду
↓
получает экипировку
↓
участвует в вылазке
↓
получает травму
↓
лечится
↓
создаёт отношения
↓
может погибнуть
↓
остаётся тело и инвентарь
↓
группа реагирует
↓
меняется мораль
↓
меняется поведение
↓
мир продолжает жить
```

Именно такие цепочки являются основой проекта.
